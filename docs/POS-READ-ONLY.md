# The AI never writes to the shop program

This is the first rule of the AI assistant 2.0 work (the owner's brief of 12 October 2026, recorded word for word in `docs/OWNER-REQUESTS.md`): **the AI never writes to or changes the live POS database, the POS's files, the POS's settings or the POS's business records.** What it may keep is its **own** data (chat history, memory, plan and tasks, campaigns, notes), in files of the add-on's own data folder, apart from the shop's database.

The protection has several layers, so that the failure of one does not matter. Each layer says where it is in the code and which test pins it. What a test cannot show (the real SQL Server) is listed at the end.

## The layers

| # | Layer | Where | Pinned by |
|---|---|---|---|
| 1 | **The assistant has no way to write the shop.** Its tools are a short written list; none may reach the shop's database, files or settings (`ToolReach.ShopWrite` is refused when the list is built); a tool that goes outside the PC or spends money must wait for the owner. The AI does not run commands, read files or open a connection: the application runs one of these tools on a route it chose. | `SmartRetail.AI.Core/Assistant/AssistantTools.cs` | `PosReadOnlyTests.The_assistants_tools_are_a_fixed_list...`, `...A_tool_that_reaches_outside...` |
| 2 | **Only a few places can open a connection to the shop's database at all.** A test lists them: the side panel's executor, the dashboard's chat executor and the dashboard's own parameterised reads. Each runs inside a transaction that is never committed. Anyone who adds another way gets a failing test and must have it reviewed. | `Desktop/SqlServerQueryExecutor.cs`, `Web/Services/SqlClientQueryExecutor.cs`, `Pos.Data/SqlServer/SqlDb.cs` | `PosReadOnlyTests.Only_the_read_only_executors...` |
| 3 | **No source of the assistant or the dashboard holds a statement that writes** (`INSERT INTO`, `UPDATE … SET`, `DELETE FROM`, `TRUNCATE`, `DROP`, `ALTER`, `CREATE TABLE`, `EXEC sp_/xp_`), and none writes a file of the POS (its database files, `SQLSettings.dat`, its program folder). | whole `src` of both apps | `PosReadOnlyTests.No_source...`, `...The_assistant_and_the_dashboard_hold_no_path...` |
| 4 | **The safety check (`SqlGuard`).** One statement only; it must start with `SELECT` or `WITH`; every write word is refused wherever it hides (after `;`, inside a `WITH`, behind a comment, in any case), also `INTO`, `EXEC`, `OPENROWSET`, `OPENQUERY`, `WAITFOR`, locking hints, `NEXT VALUE FOR` (it changes a sequence), variables and temporary tables, system procedures and views, `master..x`, three-part names, another schema, functions used as tables, and tables that are not on the approved list (passwords, keys, licence data, bank details). A refusal says why, so the AI can correct the query. | `SmartRetail.AI.Core/Data/SqlGuard.cs` | `SqlGuardTests` and `PosReadOnlyTests` (about 100 attack queries, and a check that every keyword the guard lists is refused in 8 positions and 3 spellings) |
| 5 | **A transaction that is rolled back.** Every read runs at `READ UNCOMMITTED` with a lock timeout, a command timeout and a row limit, and is never committed, so even a statement that got past layer 4 could not change anything. Personal details are hidden from the AI (`PiiMasker`). | the three executors of layer 2 | `PosReadOnlyTests` (no `Commit` in them) |
| 6 | **The database's own protection: an account that can only read.** `sql/create_readonly_login.sql` makes a login that is a member of `db_datareader`, is denied every kind of change (`db_denydatawriter`, `db_denyddladmin`, and `DENY` on `INSERT`, `UPDATE`, `DELETE`, `EXECUTE`, `ALTER`, `CREATE`) and cannot see the tables of passwords, keys, licence data and bank details. The assistant can **ask the database what the account in use may do** and says so in plain words (Settings → Database login → *Check now*). | `sql/create_readonly_login.sql`, `Data/PosAccessCheck.cs` | `PosAccessTests` (the decision; the real SQL Server is not tested here) |
| 7 | **Fail closed, if the owner asks.** The setting *Read the shop's data only with a read-only database login* (Privacy, in the settings window) makes the assistant ask nothing of the shop's data until the account is shown to be one: an account that can change data, or one that could not be checked, gets a plain refusal with the steps. Advice and planning questions, which need no shop data, still work. | `Assistant/BusinessAssistant.cs` | `PosAccessTests` (4 cases) |
| 8 | **The assistant's own writes are its own.** Memory, plan and tasks, campaigns, past chats and posters are files under the add-on's data folder (`Memory\memory.json`, `Memory\work.json`, `Memory\Chats\…`), written by one store each, with a size limit, a check of every entry (no instruction to the AI, no hidden characters), a journey that records every change and an undo. What the AI suggests for the plan is in a fixed shape that cannot express a database, a file or a command; it waits for the owner's Save unless the owner switched that off. | `Work/WorkStore.cs`, `Work/WorkRules.cs`, `Work/WorkExtraction.cs`, `Memory/*` | `WorkTests`, `CampaignTests`, `PosReadOnlyTests.The_plan_store_cannot_be_pointed_at...` |

## What to do on a PC: make the read-only login (one time, by a person)

The assistant can borrow the login the POS itself uses, which is `sa`, a full administrator. Layers 1 to 5 mean it still never writes. Layer 6 removes even the possibility, and it needs one person with an administrator's rights, once:

1. On the PC that holds the POS database, open **SQL Server Management Studio** and sign in as an administrator (or use `sqlcmd`).
2. Open `sql\create_readonly_login.sql` (it is in the AI add-on's folder and a separate file of each release). Replace `CHANGE-ME-Use-A-Long-Password-2026!` with a long password of your own, and write the company database(s) in the list `@CompanyDatabases` (the POS names them `Raintech_DB1`, `Raintech_DB2`, …). Press **Execute**. It prints "Read-only access set up in …" for each database. It can be run again safely.
3. In the assistant: *Settings → Database*: untick **Windows authentication**, set **SQL login** to `smartretail_ai` and **Password** to the one you chose, then **Test connection**.
4. In the dashboard: *Settings → Database login → **Check now***. It must say "can only read". If it names a right the login still has, the script did not finish on that database.
5. Optional but recommended: in the settings window, *Privacy*, tick **Read the shop's data only with a read-only database login**.

**Not verified here:** this script and the check on a real SQL Server (there is none here); that the dashboard's page of the POS log still reads with this login (the script was made for it). The first person to run it should say what they saw.

## What this does not claim

- It does not claim that the assistant is "secure" or "bug-free". It says what was tested: the safety check against about 100 attack queries and every keyword it lists; the places that open a connection; the absence of write statements and of writes to the POS's files in the source; the tools; the decision of the account check; the plan store's rules.
- The older Windows POS (`apps/pos-desktop`) writes to its own database, because it is the POS. This document is about the AI add-on and the dashboard.
- A person with administrator rights on the PC can still change anything by hand. The rule is about the AI.

The direction and the rules are in `docs/VERSION-2.md` and `CLAUDE.md`, section 15.

## 3. Decisions

1. **The host is the Business Hub.** It is the program for every kind of business, the one that is white-label and runs on Windows and Linux, and it already has the licence gate, users, permissions and an audit log. The Windows POS and the AI add-on become **source systems** later (their read-only adapters feed events), not the host.
2. **New code starts inside `NextGenOS.Hub.Core` (folder `Ai/`)**, written so that it depends on nothing of the Hub except a small database interface, so it can move to `libs/dotnet` when the add-on or the dashboard needs it. A new assembly now would add a new program to hide (Obfuscar) and to audit, for no gain yet.
3. **The existing C# providers are adopted by adapter later, not rewritten.** Phase 1 adds the contracts and one real adapter (an OpenAI-compatible endpoint, which covers Ollama, llama.cpp, vLLM, a LAN server and OpenRouter).
4. **New tables only, and every one carries `tenant_id` and `site_id`** (defaults `local` and `main`). Nothing existing changes. Retrofitting these ids later would touch every table and query.
5. **Everything starts off.** Every AI feature flag defaults to off; no model is downloaded; no network call is made unless the owner has configured a provider and consented to the data classes it may receive.
6. **The licence module `ai` already exists** in the format (plans `business` and above). The Hub starts checking it for the AI settings; no format change, so no change to the three licence libraries (`CLAUDE.md` section 4).
7. **One secret store contract.** Windows Credential Manager on Windows; an encrypted vault file elsewhere; never plaintext (`CLAUDE.md` section 15).
8. **Migrations get a safety net first:** a copy of `shop.db` before any pending migration runs, and a tested "down" script for every new migration (forward-only, no backup, and untested upgrades today).

## 5. Debt and blockers that matter

- No event or outbox layer, no idempotency keys (safety comes from status checks and unique constraints).
- No tenancy; limits in the licence (devices, stores, users) are not enforced by the Hub.
- Migrations: forward-only, no checksum, no backup, and the upgrade path has never run on a real old database (only `001` exists).
- `audit_log` is append-only by convention only: no trigger, no hash chain.
- Roles are fixed in code, and services do not check permissions themselves (pages and endpoints do). An AI assistant that calls services directly would skip them: **every AI tool must go through an explicit permission check** (Phase 6).
- Obfuscar renames types and fields: no persisted type names from reflection in new code.
- Anything native or any model file must be bundled and pass `scripts/audit-prerequisites.mjs`; shared tax code must still compile on net48 and C# 10.
- **Findings in the existing AI code that conflict with the rules and must be fixed** (listed in `docs/OPEN-WORK.md`): the add-on's "Ask AI" sends hosted providers customer names, cities, states and remarks (the README says personal data is hidden; names are not), plus the table and column layout, photos and the typed question unmasked, and masking can be switched off; the Setup Studio keeps API keys in a plaintext file; DPAPI secrets cannot be saved on Linux; the add-on's prompts and PII masking are India-specific (`CLAUDE.md` section 8); no AI audit trail or cost tracking exists anywhere.

## 6. The smallest safe Phase 1 (what is built first)

**In:** feature flags (a general mechanism, all AI flags off); a hardware capability service and profile (`LIGHT_LOCAL` to `ENTERPRISE_SERVER`) with honest "unknown" where a probe is not possible; the provider contracts (`LLMProvider`, `EmbeddingProvider`, `VisionProvider`, `SpeechProvider`, `OCRProvider`, `RerankerProvider`, `ObjectDetectionProvider`, `SegmentationProvider`, `TrackingProvider`) and one real adapter (OpenAI-compatible); a provider registry; data classification and a routing policy (local first, never leaving for `PAYMENT_SENSITIVE`, raw video local by default) as pure, tested logic with a recorded reason for every decision; a model registry (what is configured, its status, never an automatic download); a secret store; consent records; the migration (new tables, with a down script and a backup first); an **AI** tab in Settings behind the `ai` licence module and an `ai.manage` permission; audit entries for every change; tests; documentation.

**Out, on purpose:** events, ontology, rules, embeddings, RAG, the assistant, cameras, predictions (Phases 2 to 8); downloading or running a model; any remote call by default; any change to checkout, tax, payment or stock code.

## 7. Phase 2: what was built (and what was not)

Everything is in `apps/business-hub/src/NextGenOS.Hub.Core/Events/` (and the screen in `Web/Components/Pages/EventHistory.razor`). Run: the Hub's test projects, and `apps/business-hub/e2e/events.e2e.mjs` in a real Chromium.

| Piece | What it does | Where it stops |
|---|---|---|
| **Two kinds of record, kept apart** | An **observation** is what a model or a sensor saw (uncertain, plentiful, short-lived, never a business fact). An **event** is a business fact with who or what, which thing, where, when, how sure, why the system believes it, what made it (a rule, a model, a person, the program, an import), and which observations and which evidence it rests on. | The event types are free dotted names (`customer_session.picked_up_product`), not a fixed catalogue: the catalogue and the mapping of the shop's own records into it come with the ontology (Phase 3). |
| **Append-only** (`EventStore.cs`) | Rows are only added. A wrong event is marked rejected; a correction is a new event that points back at the old one, which is marked replaced; both stay and the history reads as it was. The same fact sent twice with the same key is kept once. A record is refused whole when any part is wrong. | Nothing stops someone with the database file from editing it by hand (`audit_log` has the same limit). |
| **Provenance** (`Explain`) | "Why does the system believe this?": what made it and its version, how sure, the explanation text, the observations and evidence it rests on, what it corrects and what replaced it, and how many of its observations have been forgotten since. | The explanation text is written by whatever made the event; the program does not check that it is true. |
| **Evidence is a pointer** | A picture, clip or document is a reference (and a fingerprint) to a file kept elsewhere; the store never holds the content. | Nothing yet keeps those files: the camera storage (Phase 7) will, and deletes what the forgetting lists. |
| **Anonymous by default** (`EventRules`) | People and things are named by opaque references (`track:cam1:17`, `user:5`, `product:123`): a name, an e-mail address or a phone number with spaces is refused. Card and payment details are never kept (refused by kind and by a card-number check in every text part). | A reference could still be built from a person's identity by a careless source (an id that is a phone number without spaces); the first sources are ours. |
| **Retention and forgetting** (`Retention.cs`) | Every record carries the day it may be forgotten, from the owner's rules or short defaults (camera and sound observations 3 days, personal observations 7, other observations 14; events 365, personal 90; evidence 30, camera 7). Biometric data is not kept at all unless the owner writes a number of days (the opt-in). The background worker forgets what is past its day every ten minutes, **whatever the switches say**, and lists the evidence references that were forgotten. | The forgetting is of this program's records; copies in a backup made before the day stay in that backup. |
| **The switch** | Writing needs the owner's switch "Business event history" and the licence's `ai` part; reading, confirming or rejecting, and forgetting do not. | The shop's own sales, voids and stock changes do not write events yet. |
| **Screen** | *Settings, AI helpers, Business events* (owner only): what is kept, a filter by what, start of the type, standing and days, "Why?", "Yes, it happened" and "No, it was wrong" for events that are only proposed, the retention rules, and "forget what is past its time now". | No ingest interface for other programs: an edge box or a camera service will need an authenticated way in (Phase 7 and the edge and cloud work). |
| **Database** (`Data/Migrations/003_event_foundation.sql`) | Five new tables with `tenant_id` and `site_id`, only added, and a tested way back for this step alone. | As for step 2: never run on a real, old shop database. |

## 9. Phase 4, steps 1 and 2: what was built (and what was not)

Everything is in `apps/business-hub/src/NextGenOS.Hub.Core/Intelligence/` (and two boxes on the screen *Settings, AI helpers, Business events*, `Web/Components/Pages/EventHistory.razor`). Run: `StateTests` and `RuleTests` in the Hub's tests, and `apps/business-hub/e2e/events.e2e.mjs` in a real Chromium.

**Step 1: why it is small.** Phase 4 is "projections, current state, rules engine, analytics". The shop already has its sales, stock and money in tables and reports, so a second copy of those as "state" would only drift from the truth. What does not exist anywhere is *what the event history says is true about one thing or one place now*, and that is what the digital twin of cameras, shelves and devices (Phase 7) will need. The first step answers exactly that question, and nothing else, so that it can be trusted before more is put on it.

| Piece | What it does | Where it stops |
|---|---|---|
| **State from the events, asked for when needed** (`StateService.Of`, `OfZone`) | For a thing (`item:12`, `track:cam1:17`) or a place (`zone:entrance`): the newest **confirmed** event, how many events there are of each kind, when the thing was first heard of and how long it has been quiet, and a sentence in plain words. Events still waiting to be checked are counted apart and never decide what is true; wrong and replaced events are left out. | Only what the events already say. Nothing is added up across things (a shelf's estimated stock, a queue's length): that needs events that nothing writes yet. |
| **No second copy** | The answer is worked out from the `events` table at the moment of asking, so a correction (an event marked wrong, a replacement) shows at once and nothing can drift. There is **no new table**. | If the history grows very large, a stored summary may become worth having; it would be added then, with a way to rebuild it from the events. |
| **An earlier moment** (`at`) | The same question about an earlier moment gives the state as the history *now* says it was then (a later event is ignored; an event since found wrong is left out). | It is not "what we believed at the time": the history does not keep the earlier standing of an event, only the audit line of the change. |
| **What was active lately** (`Active`) | The things that had a confirmed event in a period (default a day, at most a year), most recent first, narrowed by the start of a reference; at most 200. | Things only; places are asked one at a time. |
| **Who may ask** | The same people who may open the event history (the AI helpers' permission), because the history holds every kind of data. Nobody signed in is refused. The answer holds the kind of event, the time, how sure the system is and what made it, **never the data inside an event**. A name, an e-mail address, a phone number or a wild card is refused as a reference. | The kind-of-information rules of the business map (`ReadPolicy`) are not applied here: this is the owner's screen. They must be applied before the assistant (Phase 6) is given this. |
| **The switches** | Reading needs no switch, like the history itself: what was kept can always be looked at, also after the history is switched off or the licence ends. Nothing is written by asking (a test counts every table before and after). | No new switch: the step reads the history and adds no behaviour. The rules engine (next) will sit behind "Advanced automatic rules", off by default. |
| **Database** (`Data/Migrations/028_event_subject_index.sql`) | Two **indexes** on the event history (by thing and by place), so that the question reads only that thing's events. No table, column or row is changed or removed. A test shows the question uses the index, and that the step can be undone alone (`Rollbacks/028_event_subject_index.sql`) with every event kept, and done again. | As for the earlier steps: never run on a real, old shop database. Building an index on a very large history takes a moment the first time the program starts after the update (the update makes a checked copy first, as for every step). |

### Step 2: automatic rules that can only propose

A rule is **data in a fixed shape**: "when N or more confirmed events whose type starts with X, each at least P% sure, happen about the same thing (or in the same place, or anywhere) within M minutes, propose an event of type Y". The shape has no place to say "do" anything, so a rule cannot send, change or delete anything: **the only thing it ever produces is a proposed event** in the business event history, made by "an automatic rule", which a person confirms or rejects (the same screen and the same "Why?" as every other event). That is the rule of `docs/VERSION-2.md` for consequential actions: the system recommends, a person approves.

| Piece | What it does | Where it stops |
|---|---|---|
| **Rules as data** (`RuleService`, tables `event_rules`, `event_rule_firings`) | Make, change, switch on or off and retire a rule; at most 50 in use; every part is checked (types are lower-case words joined by dots, numbers have sensible limits, no card number in a note); every change is in the audit record with who made it. A rule is made **switched off**. Changing one makes a new version and switches it off again. Retired rules stay on record. | Only counting events of one kind by thing, place or everywhere. No "and", "or", "if the stock is below", no reading of the shop's tables, no sequences ("A then B"). Those are for a later step, and will be added as data, never as code a rule carries. |
| **Looks only forward** | A rule switched on at a moment looks only at events **recorded after** that moment; it never makes a burst of proposals from old history. Where it has got to is kept (time and event number), so a burst of thousands of events is worked through in passes of 500 and no event is read twice from the start. | An event that was only *proposed* when a rule looked, and which a person confirms later, counts in later windows but does not start a trigger by itself (a test pins this). Rules do not look at an event's later change of standing. |
| **Once per trigger** | One trigger fires at most once, remembered in the database (also if the program stops between writing the proposal and writing the note: the history keeps one event for one trigger). The same thing or place does not fire again within the rule's time. | |
| **No chains** | What rules made is never counted by rules, not even once a person has confirmed it, so rules cannot feed each other or themselves. | |
| **Provenance** | A proposal says which rule (and which version) made it, how many events it counted and the numbers of up to 20 of them, and why in words; it has the same kind of data as the events that caused it (so retention rules apply to it). The data inside the triggering events is not copied. | |
| **Switches and licence** | Runs only while the licence has the AI part and both "Business event history" and "Advanced automatic rules" are on. Off: nothing runs, no rule loses its place, and what was proposed stays. From the shop's upkeep (never the till's path; a failure never stops the rest of the upkeep) and from the button "Look at the events now". | A rule is not run by a timer of its own faster than the shop's upkeep. |
| **Who may** | The AI helpers' permission (owners); nobody signed in is refused. | |
| **Screen** | A box "Automatic rules" on the Business events screen: the list in plain words with On/Off, make or change a rule, switch on/off, retire, "Look at the events now". | No test run ("what would this have done last week?") yet. |
| **Database** (`Data/Migrations/029_event_rules.sql`) | Two new tables with `tenant_id` and `site_id`, only added, and a tested way back (`Rollbacks/029_event_rules.sql`) that keeps every event and proposal. | As for the earlier steps: never run on a real, old shop database. |

**Not built in Phase 4 yet:** states worked out from many events (a shelf's estimated stock, a queue's length); richer rules (conditions on more than one kind of event, sequences, a rule that proposes a *task* for staff); a "what would this rule have done last week?" test run; analytics over time; a stored projection with a checkpoint (only when the size needs it). **Not verified:** the two boxes on a real Windows PC with a real, large history; the speed of the questions on a history of millions of events; the rules on a real stream of camera events (none exist until Phase 7).

## 10. Phase 5, step 1: what was built (and what was not)

Everything is in `apps/business-hub/src/NextGenOS.Hub.Core/Knowledge/` and the screen *Settings, AI helpers, Notes to search* (`Web/Components/Pages/Knowledge.razor`). Run: `KnowledgeTests` in the Hub's tests and `apps/business-hub/e2e/knowledge.e2e.mjs` in a real Chromium.

**What exists already and is reused** (looked for first, `CLAUDE.md` section 17): the embedding contract and its first adapter (`IEmbeddingProvider`, `OpenAiCompatibleProvider`), the one door to every AI service (`AiGateway.EmbedAsync`: licence, switch, privacy routing, limits, record of use), the switch `local_embeddings` ("Search by meaning"), and the business map's rule for who may read what (`ReadPolicy`). The storefront's pgvector and the dashboard's JSON vector file are other programs' and are not touched. **What was missing, and is new:** somewhere to keep text with its vectors, a vector-store interface the business code can talk to, cutting text into pieces, and a search that points at its sources.

| Piece | What it does | Where it stops |
|---|---|---|
| **The owner's notes** (`KnowledgeService`, tables `knowledge_sources`, `knowledge_chunks`) | A note has a title, the kind of information it holds (public, internal, confidential, personal or financial: chosen by the owner, default confidential) and its words, kept in short pieces in the shop's own file, with a reference (`note:7`) an answer can point at. Card and payment details, fingerprints and faces are never kept; a card number in the words is refused. At most 500 notes and 20,000 pieces. Changing a note replaces its pieces and forgets their vectors; **retiring a note deletes its words and its vectors**. Every change is in the audit record, without the words. | Only typed notes. No documents, pictures, scans or the shop's own records yet (the business map's products, people and bills are not searched). |
| **Vector store behind an interface** (`IVectorIndex`, `SqliteVectorIndex`) | The business code never names a vector database. Today vectors are kept in the shop's file and a question is compared with every vector made by the same model (exact, nothing to install, quick for thousands of pieces); numbers are made unit length; vectors of different models are never compared; a vector that is empty, not finite or all zeros is refused. | No fast index for very large collections. pgvector and Qdrant adapters are **not written**; the interface is where they would go. |
| **Making vectors** (`PrepareAsync`) | Goes through the same door as all AI work, one kind of information at a time, so the privacy rules judge each as what it is: a note about people is never sent to an online service that was not allowed it, and a service on this computer may receive all kinds. A refusal, a service that does not answer or an answer that cannot be used stops the pass quietly with a reason; the notes stay. | The owner presses *Prepare the notes now* (no background timer yet). Tested with a stand-in service; **no real local model has been tried**. |
| **Search** (`SearchAsync`) | **Words always work**, with every AI service off: each word counts for more the fewer pieces hold it, so no list of words to ignore is needed and any language works. When "Search by meaning" is on, vectors exist and a service may receive the question, meaning counts too (a question about "inexpensive" finds a note that says "cheap"); the answer says which hits came from meaning and, when meaning was not used, why not. Every hit carries the note's reference, title and the piece that matched. | The mix of meaning and words (70 percent / 30 percent) and the least likeness that counts (0.2) are first guesses, not measured on real notes. No re-ranking model yet. |
| **What a person may read** | A hit is shown only when the person asking may see that kind of information elsewhere in the shop (`ReadPolicy`): a cashier finds public, internal and personal notes (the customer list) but not confidential or financial ones; the kitchen screen finds public and internal only; nobody signed in is refused. The same filter applies to what the vectors find. | The assistant (Phase 6) will have to call this the same way, as the person asking. |
| **Who may write** | The AI helpers' permission (owners), the licence's AI part and the switch for writing and making vectors; looking at the list, retiring and searching by words never need the switch. | |
| **Database** (`Data/Migrations/030_knowledge.sql`) | Two new tables with `tenant_id` and `site_id`, only added, and a tested way back (`Rollbacks/030_knowledge.sql`) that leaves the shop's records alone. | As for the earlier steps: never run on a real, old shop database. |

**Not built in Phase 5 yet:** reading documents (files, scans, OCR), the shop's own records as knowledge, a background timer that prepares notes, a re-ranking model, pgvector and Qdrant adapters, a downloadable local model (no model is ever downloaded without the owner's permission, `CLAUDE.md` section 15), and answers that quote their sources in a written reply (that is the assistant, Phase 6). **Not verified:** a real local embedding model; a large collection (speed beyond a few thousand pieces); the screen on a real Windows PC.

## 11. Phase 6, step 1: what was built (and what was not)

Everything is in `apps/business-hub/src/NextGenOS.Hub.Core/Assistant/` and the screen *Ask the shop* (`Web/Components/Pages/Ask.razor`; its menu entry appears only while the switch is on). Run: `AssistantTests` in the Hub's tests and `apps/business-hub/e2e/assistant.e2e.mjs` in a real Chromium, which talks to a small stand-in AI program that speaks the same web language as the usual local AI programs, so the real connection is used.

**What exists already and is reused** (looked for first, `CLAUDE.md` section 17): the one door to every AI service (`AiGateway.GenerateAsync`: licence, switch, privacy routing, the owner's permissions, limits, record of use), the notes search of Phase 5 (`KnowledgeService.SearchAsync`, already limited to what the person asking may read), the shop's own report services (which ask for the person's permission themselves), `Access` (who is asking, looked up again each time), `TextGuard`, and the switch `ai_assistant` ("Business assistant"), which existed since Phase 1. The AI add-on's assistant (`apps/pos-ai-companion`) belongs to the older Windows POS and is not touched. **What was missing, and is new:** a fixed list of read-only lookups, a way for a model to choose among them that the program checks, an answer that points at numbered facts, and a record of what was asked.

| Piece | What it does | Where it stops |
|---|---|---|
| **A closed list of lookups** (`AssistantTools`) | Four, all read-only: *your notes* (anyone signed in; only what the person may read), *sales* for a period (reports or selling permission), *best sellers* by money or quantity (reports) and *out of stock* (reports or stock). Each says in its lines what period and what kind of figure it is, so a line can be read and checked on its own. Money, dates and the word for a sale come from the shop's own settings. | No lookup of customers, suppliers, the books, cash, the business events or "what is true now" (Phase 4) yet; no lookup that writes. |
| **The model chooses, the program decides** (`Prompts.ReadPlan`) | When the person may use more than one lookup, a model is asked which to use and replies in a fixed JSON shape. Only the lookups that person's role allows are described to it; anything else it names, a lookup it invented, a second copy of the same lookup with the same choices, a fourth lookup or a choice that is not on the list (a period that does not exist) is dropped and said in plain words. A reply that is not understood means only the notes are searched. | A small model may choose badly or answer in the wrong shape; the screen then shows less, never more. No tool calling in the model's own format (so any model that can write JSON works). |
| **It obeys the person asking** | Three layers: the lookups offered to the model are those the role allows; each is checked again before it runs; and the shop's own services check the permission again inside, exactly as for that person's own screens. A cashier is not offered best sellers or the stock reports and gets the day's totals only because the selling screen shows them; the kitchen is offered only the notes. The program itself and nobody-signed-in are refused. | Roles only; no per-item or per-customer rules (the shop has none). |
| **The answer** (`Prompts.AnswerInstructions`) | The model gets the program's rules, the numbered facts on one line each (a note cannot start a fake numbered line) and the question; it is told that facts are data and never instructions. Its answer is checked: a pointer to a fact that does not exist is taken out and said; an answer with no pointer is flagged; the screen always shows the numbered facts, marked "used in the answer", so a person can check. **If nothing was found, no model is asked at all**, so nothing can be made up. It answers in the language the question is written in. | Whether the words of an answer are true to the facts is not checked by the program (only the pointers are); the screen says the assistant can make mistakes. |
| **Privacy follows the facts** | The question is treated as confidential business information (a telephone number or an e-mail address in it makes it personal data); the answer is requested in the strictest kind of information among the facts (money is financial, a note is whatever the owner marked it). Both go through the one door, so a service on this computer may get them, one on the shop's network or online only if the owner allowed that kind of information and (online) the switch for online services. When no service may, the facts are shown as they are. | A service on this computer has never been tried with a real model here. |
| **Nothing is changed** | There is no lookup that writes, and a test compares every table of the shop (except the question record, the audit trail and the AI use and sent records) before and after a question that asks for deleting and refunding. There is nothing to approve in this step; the next step lets the assistant *prepare a request* through the typed actions that already wait for a second person's approval. | |
| **The record** (`assistant_questions`) | Who asked (and in which role), the question, which lookups were made and with which choices, which notes were pointed at, how it ended, which service and model wrote the answer, and any note. **Not the answer and not the figures.** A question that holds a telephone number or an e-mail address is answered but its words are not kept. Forgotten after 90 days by the upkeep. A person sees their own questions; the people who may use the AI helpers see everyone's. The audit trail holds the lookups and the outcome, never the words. | The 90 days are a fixed number, not yet a setting. |
| **Limits** | At most two questions at once (a third is asked to wait), 30 questions an hour for each person, 500 letters for a question, 120 seconds for a question as a whole (a slow service is given up on, quietly), 30 facts, 3 lookups besides the notes. The providers' own daily and monthly limits apply as for all AI work. | |
| **Database** (`Data/Migrations/031_assistant.sql`) | One new table with `tenant_id` and `site_id`, only added, and a tested way back (`Rollbacks/031_assistant.sql`) that leaves the shop's records and notes alone. | As for the earlier steps: never run on a real, old shop database. |

## 12. Phase 7, step 1: the camera register (what was built, and what was not)

Added on 23 October 2026. Everything is in `apps/business-hub/src/NextGenOS.Hub.Core/Cameras/` and the screen *Settings, AI helpers, Cameras* (`/settings/cameras`, `Web/Components/Pages/Cameras.razor`). Run: `CameraTests` in the Hub's tests, a test of the screen's access in the web tests, and `apps/business-hub/e2e/cameras.e2e.mjs` in a real Chromium, which uses a small stand-in "camera" of its own that only counts what it is sent.

**The smallest safe step.** This step keeps a *list* of the shop's cameras and can ask "does it answer?". **It reads no picture and no video, finds no one and writes no observation or event**; nothing here watches anything. The steps that follow (taking a picture from a stream, finding people and trolleys in it, writing what was found as observations, then events with thresholds) are separate and each needs its own test.

**What exists already and is reused** (looked for first, `CLAUDE.md` section 17): the switch `camera_analytics` ("Camera analytics", off by default, needs the licence's AI part; it has existed since Phase 1), the secret store (`ISecretStore`: the computer's own safe place), `EndpointClassifier` (the same test of "this computer or the shop's own network" that decides where an AI service may be), `Access`, `AuditService`, the migration system. **New:** the register, its checks, the reachability test and the screen.

| Piece | What it does | Where it stops |
|---|---|---|
| **Off until the owner says so** | Nothing can be added, changed or tested while "Camera analytics" is off or the licence lacks the AI part (`cameras-off`, `not-licensed`). Every new camera starts switched off, and a camera can be switched on only after the program has reached it (a camera plugged into this computer cannot be checked from here, so the owner's word is what there is). Switching off is always possible. Changing a camera's kind or address switches it off again and forgets the check. | A camera that is "on" is **not read** in this step: the switch records the owner's choice for the steps that follow, and the screen says so. |
| **Only the owner** | Every call asks for the AI helpers' permission (owners); a manager, a cashier and nobody signed in are refused, also for the list and for one camera. | |
| **The shop's own network only** | A network camera's address must be on this computer (127.x, `localhost`, `::1`), a private range (10.x, 172.16-31.x, 192.168.x), link-local, or a plain machine name (`cam1`, `hall.local`). An internet address is refused (`outside-network`). When the test connects, the address it **actually reached** is looked at again, so a name that leads outside is not used either. | A name that points inside when it is added and outside later is stopped at the connection by that second look. The second look itself is tested on its own (public, private, loopback and link-local addresses, and none at all); the whole case with a real name that changes its answer needs a real name server and is not tested end to end. |
| **No password in the register** | An address with a user name or password is refused (`password-in-address`). A camera's password has its own box on the edit screen, is kept in the secret store under `camera/<id>`, and is never in the database, the audit trail, an error message or a screen again: the list says only "password kept". A retired camera's password is deleted. | If the safe place is damaged the program says "no password" rather than failing. |
| **No faces** | What a camera may look for is a closed list: people (anonymous: only that someone is there), trolleys, baskets, products. There is no entry for a face, a name or a plate, none can be typed in, and the screen says the program does not look at faces and does not know who anyone is. | The detection itself is not built; this only fixes what may ever be asked of a camera. |
| **Kinds and addresses** | Network stream (`rtsp://` or `rtsps://`), ONVIF (an address or `http(s)://` URL), a camera plugged into this computer (the name the computer gives it, letters and numbers only), and a video or picture file on this computer (a known picture or video extension, no `..`, no file on another computer). | ONVIF is only an address here: nothing is discovered or controlled. |
| **"Does it answer?"** (`TestAsync`) | A network camera is only **connected to and let go** (3 seconds at most): not one byte is sent, so no request and no picture is asked for (a test checks that a listening door receives zero bytes). A file is looked for. A plugged-in camera says it cannot be checked from here. The answer and the time are written down. | A camera that answers on its port may still not give a picture; only a later step can know. |
| **What else** | A short reference for each (`camera:front-door`; a second with the same name gets `-2`), an optional place (`zone:aisle-3`, written like the business map's places), how sure the program must be (10 to 99 percent, 50 at the start), at most 64 cameras, retiring (the row stays; switched off, password deleted). | The place is checked for its shape only, not against the business map yet. |
| **The record** | The audit trail gets `camera.add`, `.update`, `.enable`, `.disable`, `.test`, `.password`, `.password-removed`, `.retire`, each with the camera's name and never its address or password. | |
| **Nothing leaves the shop** | Nothing in the register is sent to any AI service or anywhere else; the page says pictures and video never leave this computer. | |
| **Database** (`Data/Migrations/032_cameras.sql`) | One new table with `tenant_id` and `site_id`, only added, and a tested way back (`Rollbacks/032_cameras.sql`) that leaves the shop's records and the earlier steps alone. The table has no column for a password or a picture. | As for the earlier steps: never run on a real, old shop database. |

**Not built (the next steps of Phase 7):** reading a stream or a file; the decision how to decode video (the owner's rules rule out a GPL build of a video library and require everything to be bundled, so this needs an owner decision: for example a bundled LGPL build of ffmpeg, checked by the package audit); which detection model, and its licence and size (no model is downloaded without the owner's permission); detection and tracking; zones and lines; observations and events from cameras; where clips are kept and for how long; ONVIF discovery; checking a plugged-in camera; a camera's health over time. **Not verified:** any real camera, USB device or video stream (this was only tried against a stand-in that accepts a connection); the screen on a real Windows PC; the migration on a real old shop database.

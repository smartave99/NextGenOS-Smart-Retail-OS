## What to know first

1. **Two programs, one product.** The add-on (`apps/pos-ai-companion`, net48 + net8) is a Windows shell plus an engine library, `SmartRetail.AI.Core` (providers, `SqlGuard`, `PiiMasker`, memory, photo/poster/creative prompts, settings). The dashboard (`apps/pos-dashboard-service`, .NET 10 Blazor) holds almost every screen and all the analytics, and builds `AI.Core` into itself (A1, B1). Both read the old POS's SQL Server **read-only**; its table layout survives only in `AI.Core/Data/PosSchemaData.cs` and the dashboard's test fixture (A4).
2. **Best thing to reuse:** `SmartRetail.Pos.Core` (net10, pure, no I/O): billing and money rounding, sales analysis, Fix now checks, actions, Monday review, poster offer rules, labels, owner payloads, with their tests. It reads data only through six interfaces, so the Hub reuses it by implementing them over SQLite (B1, B1b, C3).
3. **Eight providers behind `IAiProvider`** (Codex, Claude and Antigravity CLIs, OpenAI, Anthropic, Gemini, OpenAI-compatible, custom CLI), a router with fall-back (explicit choice never falls back; the same provider answers both steps of Ask AI), and 11 jobs each with a model and a thinking level (A2). **Only Codex** reads photos and voice and makes pictures. The Hub has one adapter (OpenAI-compatible, chat and text embeddings) and **no contract for image generation, several images, a JSON schema, thinking level, streaming or web search** (C1, C2).
4. **`SqlGuard`** is a careful hand-made T-SQL token checker (about 50 test vectors, A4) with two real gaps: `SELECT *` on `Customer`, `Supplier` or `Company` returns bank, tax and `AdminCode` columns, and `PiiMasker` masks only phone numbers, e-mails and columns named like contacts, **not names, cities or remarks**, and only Indian number formats. The README's "personal data is hidden" is not true for names (A3).
5. **What leaves the machine:** to the owner's chosen AI vendor, the question, the table layout, up to 50 result rows (masked as above), photos, product details, stock and sales numbers for poster words, the chat for memory review; to the owner's **Supabase project**, today's bills and figures every minute, and answers of up to 100 rows; to Hugging Face, the DINOv2 model once after the owner's click; to Google, one photo on a click. Opening Get started **installs Codex from the internet by itself** (A3).
6. **Keys:** Windows DPAPI per user in `settings.json`; none can be saved on Linux. No audit, no cost record, no data classes (A3). The Hub has a vault, data classes, routing, budgets and an audit already.
7. **The owner's three "super template prompts"** (photo, poster, advertisement) are **in no code**, only in `docs/OWNER-REQUESTS.md`; `KeepTheProduct`, `PosterArtworkPrompt` and `CreativeArtPrompt` already say nearly the same "preserve, never invent" rules; a proposal for using them is in A5.
8. **Camera product search** = ZXing barcodes (always) + DINOv2 ONNX on 2 CPU threads (opt-in download, size and hash pinned), score 0.7 look + 0.3 colour, floor 0.35, "best" only when 0.05 ahead; it learns only from the add-on's own product photos (B2).
9. **Tests:** about 930 cases in the add-on and 830 in the dashboard by count (not run); the gate runs both and lets only real-Codex, SQL Server and real-DINOv2 tests skip. Most pure tests port to the Hub as characterization tests; Codex install/update, updater and WinForms tests are dropped (A6). Build state: the add-on's installer workflow is **not in the repo** and `build.ps1` still points at the old dashboard folder name (A7).
10. **Fix while porting:** India and one customer's name are fixed in prompts and screens (`₹`, Hindi, "Avenue 99"), the model name is copied across tools on fall-back, persisted enum names would break under the Hub's obfuscation, and every AI feature must be behind a flag that is off, the `ai` licence module, a data class and an audit row (A2, A3, C2, C3).

### A2. Providers, router and fallback, per-job model and thinking level

**The contract** (`AI.Core/Providers/AiProvider.cs`): `IAiProvider { Id, DisplayName, Kind (Cli or Api), CheckAsync(ct) -> ProviderStatus, CompleteAsync(AiRequest, ct) -> AiResponse }`. `AiRequest` = system prompt, user prompt, optional streaming callback `OnText`, a list of image files and a list of WAV files (lines 17 to 36). A provider that can take photos or voice notes also implements `IReadsAttachments.CannotRead(request)` (null = fine). Errors are `AiProviderException(providerId, message, canFallback, inner, usageLimit)`: `CanFallback` says whether another provider may succeed; `UsageLimit` (when the tool says the account's limit is reached, with the time it can answer again) makes background work wait instead of fail. There is no streaming of tokens through the interface except that callback, and no cost, token or usage count anywhere (the only usage figure is Codex's 5-hour/weekly limit percentage read from Codex itself).

**The eight providers** (ids in `Providers/ProviderIds.cs`; created together in `ProviderCatalog.CreateAll`, `ProviderRouter.cs` line 159):

| Id | Kind | Default model in code | How it is called | Key or sign-in | Photos / voice |
|---|---|---|---|---|---|
| `codex-cli` | CLI | none (Codex's own) | `codex exec --skip-git-repo-check --ephemeral --sandbox read-only --color never --cd <empty temp folder> --output-last-message <file> [--image f] [--model m] --config model_reasoning_effort=<level> -`; prompt on stdin (`CodexCliProvider.cs` lines 745 to 790). Base class behaviour worth knowing: CLI providers (`CliProviderBase.cs`) run in a new empty temporary folder (`Cli/RunWorkspace.cs`) deleted afterwards, with a timeout (setting `TimeoutSeconds`, default 180 s, never under 15 s), and every model or effort value passes `CheckToken` (regex `^[A-Za-z0-9][A-Za-z0-9._:/@+-]{0,99}$`, line 18, 147) before it can reach a command line. API providers (`HttpApiProviderBase.cs`) retry up to 3 times on HTTP 429 and 5xx (waiting the `Retry-After` up to 20 s, otherwise 2, 4 s), time out per setting, turn 401/403 into "rejected the API key" and 429 into "rate-limiting or out of credit"; only HTTP 400 is marked "do not fall back".

**The router** (`ProviderRouter.cs`):
1. `PlanOrder(selection)`: an explicit provider id means only that provider. `auto` means the preferred provider (if one is set), then `ProviderOrder` (default: codex-cli, claude-cli, antigravity-cli, openai-api, anthropic-api, gemini-api, openai-compatible-api, custom-cli), without duplicates, unknown ids dropped. `AssistantSettings.Normalize` repairs a hand-edited order (lines 87 to 142).
2. For each candidate: `GetStatusAsync` (`CheckAsync` sends no prompt; the result is cached 5 minutes; the cache is cleared for a provider that just failed). Not ready: with an explicit choice, stop with "<name> is not ready: ..."; in auto mode note why and go on.
3. A request with photos or voice needs `IReadsAttachments.CannotRead == null`; a provider that is not an `IReadsAttachments` is refused for it. Only Codex and the custom CLI are, so in practice **only Codex reads photos and voice**.
4. Call `CompleteAsync`. On an `AiProviderException` (not a cancel): if the choice was explicit, or `CanFallback` is false, or the setting `FallbackToOtherProviders` is off, throw; otherwise remember the failure and try the next.
5. When all are done: exactly one failure is thrown as it was; several give "No AI tool could answer." with one bullet each; none ready gives "No AI tool is ready to answer." with the reasons.
Quirk (by design, but it matters): `BusinessAssistant.AskAsync` keeps `selection = reply.ProviderId` after the first call (`BusinessAssistant.cs` line 115), so the second call (explaining the result) is an explicit choice of the provider that wrote the query: if that provider fails at the explaining step, there is no fall back to another one.

**Per-job model and thinking level** (`Settings/AiJobs.cs`): 11 jobs in `enum AiJob` (Ask, Plan, PosterWords, PosterArtwork, Photos, MemoryReview, Listing, Creative, Playbook, PriceCheck, WebsiteCategory). The owner's choices are stored in `settings.Jobs` (job name to `{Model, Effort}`; an all-empty choice is deleted, so "recommended" is the absence of an entry). Recommended thinking (`RecommendedEffort`, line 200): **Plan high; Ask, PosterWords, Listing, Creative, Playbook, PriceCheck medium; everything else low**. Which value wins (`Resolve`, line 245): the job's own choice, then what is set for the tool in Advanced settings (`settings.Codex.Model`, `.ReasoningEffort`, and the same for Claude and Antigravity), then the recommendation. "The tool" (`Tool(settings)`) is the preferred provider, or Codex when the preference is `auto`. API providers and the custom CLI get no model or level from jobs ("they choose by themselves"). `Apply(settings, job)` (line 271) writes the job's model and level into a copy of the settings for Codex, Claude CLI and Antigravity at once, and `AiEnvironment.CreateRouter(job)` (`Pos.Web/Services/AiEnvironment.cs`, the call to `Apply` is on line 77) builds a router from that copy; the Windows app applies the Ask job when it builds its own router (`Desktop/AssistantApp.cs` line 63). The level is made to fit the tool: `Fit(wanted, levels)` returns the level itself, else the highest one below it, else the lowest above; empty when there are no levels or the wanted one is unknown. The scale is none, minimal, low, medium, high, xhigh, max; Claude has low to max (5 levels), Antigravity low to high, Codex's list depends on the model and is read from Codex (`model/list` over the app server, cached 5 minutes, `Providers/CodexModelsCache.cs`; Claude's model list is read live from Anthropic with the shop's key through `CliToolCare.cs`, or a built-in list).

TEST VECTORS (from the code; `Fit` is pure): `Fit("xhigh", [low, medium, high])` gives `high`; `Fit("none", [low, medium])` gives `low`; `Fit("high", [low, medium])` gives `medium`; `Fit("medium", [])` gives empty; `Fit("bogus", [low])` gives empty. `ModelId("gpt-6.1-sol")` is accepted; a name with a space, a slash or more than 80 characters gives empty. The existing tests are `AiJobsTests.cs`, `ProviderRouterTests.cs`, `CliProviderTests.cs`, `ApiProviderTests.cs` (A6).

Quirks and probable bugs (read from code, not run):
- `AiJobs.Apply` copies the **same model string** into Codex, Claude CLI and Antigravity (lines 280, 282, 284). When auto mode falls back from Codex to Claude, a job-specific Codex model name (for example a GPT model) is passed to `claude --model`, which will fail (and then, for Antigravity, again). Probable bug; fix by keeping a model per tool.
- Claude CLI and Antigravity cannot read photos here although their tools may; a question with a photo therefore never leaves Codex.
- `openai-compatible-api` and the other API providers accept any base URL (no check that a "local" server is really on this PC or that a remote one uses https); the Hub's `Ai/Endpoints.cs` does that check (C2).
- Model names in code (`gpt-6-sol`, `claude-opus-5`, `gemini-3.5-flash`) are as written in the source; this study did not check that they exist.

What the Hub has today: `IAiProvider`-like contracts `LLMProvider` etc. in `Ai/Contracts.cs` and one adapter (OpenAI-compatible, `Ai/OpenAiCompatible.cs`); a registry, a gateway with fallback to the next allowed service, a waiting line and usage records (`Ai/Providers.cs`, `Gateway.cs`, `JobQueue.cs`, `Usage.cs`). It has **no** command-line provider (Codex, Claude, Antigravity), no per-job model or thinking level, no photo or voice input, no Anthropic or Gemini adapter. See C2 for how the old eight map on.

### A3. What leaves the machine, and where keys are kept (privacy findings)

**Where secrets are kept today**
- Windows DPAPI, scope current Windows user, with a fixed application salt (`Settings/SecretStore.cs` lines 29 to 44). Each secret is a base64 string in the dictionary `ProtectedSecrets` inside `%APPDATA%\NextGenOS\Smart Retail POS AI\settings.json` (`Settings/AssistantSettings.cs` line 84, `SettingsStore.cs`). Names (`SecretNames`, lines 7 to 14): the OpenAI, Anthropic, Gemini and OpenAI-compatible API keys, and the database password. The settings file copied to another PC or user cannot be read there (true of DPAPI; not tested here).
- On a system without DPAPI, `NoSecretProtector` throws "Secrets can only be saved on Windows" (`SecretStore.cs` line 49): **no secret can be saved on Linux**. The dashboard's owner-view key falls back to memory only (`Pos.Web/Services/OwnerViewService.cs` line 626), so it is lost at every restart off Windows.
- The owner-view PC key (to the owner's Supabase project) is DPAPI-protected in the same file (`OwnerViewSettings.ProtectedKey`); the project's URL and public key are plain settings (public by design).
- Codex keeps its own ChatGPT sign-in or OpenAI key in its own folder (this study did not look inside it). An OpenAI key typed on Get started goes to `codex login --with-api-key` on standard input (`CodexCliProvider.cs` line 713 to 721), not saved by the add-on. ### A4. SqlGuard and PiiMasker: how they work, accept and refuse examples, masking examples

**The Ask AI pipeline** (`Assistant/BusinessAssistant.cs`, `AskAsync`, lines 75 to 178), in order:
1. Refuse with a plain sentence when the owner has switched off AI-written queries (`Privacy.AllowAiWrittenQueries`).
2. Read the layout of the 22 allowed tables from `INFORMATION_SCHEMA.COLUMNS` (cached 30 minutes, key = the table list); when the login cannot read it, use the built-in copy `Data/PosSchemaData.cs` (a generated list of about 190 table names and their columns, "captured from the POS database script"; that script is not in the repository, so **this file and the dashboard's test fixture `tests/.../SqlServer/pos_schema_subset.sql` are the only surviving copy of the old POS's table layout**). Private columns (passwords, keys, bank, `AndroidID`, `BCode`) and binary types are left out of the layout shown to the AI (`SchemaCatalog.DescribeForPrompt`).
3. Ask the AI for one JSON object `{"sql": "...", "explanation": "..."}` (plus `"heard"` for a voice question). `SqlPlan.Parse` takes the first `{` to the last `}`; if that is not JSON it accepts a fenced or bare statement starting with SELECT or WITH; otherwise the whole reply is an explanation. `"sql": null` means "cannot be answered from this data": the explanation is shown, no query runs.
4. `SqlGuard.Check`. Refused: the reason is sent back to the AI as feedback with the previous query ("It could not be used: ..."), one more try. A database error (not a connection problem) is also sent back. Two attempts at most (`MaxQueryAttempts = 2`), then "The AI could not write a usable query ... Last problem: ...".
5. Run the cleaned statement (comments and trailing `;` removed) through `IQueryExecutor` with a cap of 500 rows for the screen.
6. Mask (default on) and keep at most 50 rows for the AI; a second AI call explains the result in the language of the question; the answer streams to the screen when the provider can.

**How the query is run** (`Desktop/SqlServerQueryExecutor.cs` lines 66 to 146; the dashboard has its twin `Pos.Web/Services/SqlClientQueryExecutor.cs`, which a search shows uses the same `ReadUncommitted`, the same `SET LOCK_TIMEOUT 5000` and a rollback; the rest of it was not read): a new connection per query; transaction at `ReadUncommitted`; first `SET LOCK_TIMEOUT 5000; SET NOCOUNT ON`; command timeout `max(5, DatabaseSettings.CommandTimeoutSeconds)` (default 30 s); `CommandBehavior.SingleResult`; stops at the row cap and cancels the command; `byte[]` becomes `"[binary data]"`; text is right-trimmed (the POS pads with spaces); **the transaction is always rolled back, never committed**. The recommended login only has `db_datareader` plus denies on private tables and columns (`sql/create_readonly_login.sql` lines 17 to 94), so the database is the third layer.

**What `SqlGuard` does** (`Data/SqlGuard.cs`, 549 lines; a hand-written T-SQL tokenizer, not a parser):
- Length at most 20,000 characters; not empty.
- Tokenizer removes `--` and nested `/* */` comments, understands `'...'`, `N'...'`, `[...]` and `"..."` with doubled closers; an unclosed string, identifier or comment is refused.
- Trailing `;` removed; any other `;` means "Only one SQL statement is allowed".
- The first word must be `SELECT` or `WITH`.
- Forbidden words (only as plain words): INSERT UPDATE DELETE MERGE DROP ALTER CREATE TRUNCATE EXEC EXECUTE GRANT REVOKE DENY BACKUP RESTORE SHUTDOWN DBCC KILL RECONFIGURE OPENROWSET OPENQUERY OPENDATASOURCE OPENXML BULK INTO WAITFOR USE DECLARE SET GO RAISERROR THROW CHECKPOINT READTEXT WRITETEXT UPDATETEXT TRAN TRANSACTION COMMIT ROLLBACK SAVE REVERT SETUSER INFORMATION_SCHEMA, and lock hints UPDLOCK XLOCK TABLOCK TABLOCKX HOLDLOCK PAGLOCK ROWLOCK SERIALIZABLE REPEATABLEREAD READCOMMITTEDLOCK (so a report cannot stall billing). `NOLOCK` is allowed.
- Names starting `@` or `#` (variables, temp tables), `::`, `NEXT VALUE FOR`, names starting `xp_`, `sp_`, `fn_`, names starting `sys` that are not a known POS table, any denied table, any denied column name: refused. These name checks also apply to `[quoted]` and `"quoted"` identifiers.
- `a..b` and three-part `a.b.c` names refused; `dbo.table` allowed; any other schema refused.
- After every `FROM`, `JOIN` and `APPLY` (this includes comma lists and every inner query, because the loop visits all tokens): the table must be an allowed table or a CTE name defined in the `WITH`; a function there (`name(`) is refused; `(` subqueries are skipped over and their own `FROM` is checked as the scan reaches it.
- `WITH` clause is read: each CTE must be `name [(cols)] AS ( ... )`, the main statement after it must be `SELECT`.
- The allowed table list is 22 business tables (`SchemaCatalog.BusinessTables`: InvoiceInfo, Invoice_Product, Invoice_Payment, Product, Category, SubCategory, Temp_Stock, Customer, Supplier, Stock, Stock_Product, SalesReturn, SalesReturn_Join, PurchaseReturn, PurchaseReturn_Join, Payment, CreditCustomerPayment, SalesMan, Voucher, Income, UnitMaster, Company) plus the owner's `ExtraAllowedTables`, minus 21 never-allowed tables (`DeniedTables`: Registration, Activation, EmailSetting, EmailSetting_login, EwaybillAPISetting, FTP_Category, WappApi, tbl_api_setting, SMSSetting, GSheet_setting, Autobackup, UserControl, RaintechMaster, AutoMigrationControl, DataMigration_Logs, CustomerSupportForm, Logs, Android_Apps, ExtDB, ExtDB1, ExtDB2). Denied columns: regex `pass(word)?|pwd|secret|token|api_?key|apiurl|hardwareid|activationid|admincode|(^|_)otp($|_)` (case-insensitive, unanchored) or one of the bank and identity names (AccountNumber, AccountName, Bank, Branch, IFSCCode, PAN, CIN, Bankholder, Bankacno, Bankname, Bankifsc, BankAc, BankAcN, BankAcNo, BankAcNum, BankAcNumber, BankAccount, AndroidID, BCode).

**Accept and refuse vectors** (from `tests/SmartRetail.AI.Tests/SqlGuardTests.cs`; 15 accepted lines 12 to 26, 34 refused lines 51 to 84, plus three more tests; "reason" is the substring the test looks for, case-insensitive):

Accepted: `SELECT COUNT(*) FROM InvoiceInfo`; the same in lower case; a `TOP (5)` group-by over `Invoice_Product ip JOIN Product p`; a `WITH s AS (...) SELECT TOP 10 ... JOIN s`; `WITH a (x) AS (SELECT 1), b AS (SELECT GrandTotal FROM InvoiceInfo) SELECT * FROM a, b`; the comma list `FROM Temp_Stock,Product`; `FROM dbo.InvoiceInfo i`; `[GrandTotal] FROM [dbo].[InvoiceInfo]`; a derived table `FROM (SELECT SUM(GrandTotal) ...) AS x`; `FROM InvoiceInfo WITH (NOLOCK)`; a LEFT JOIN with `IS NULL`; a nested comment `/* a /* nested */ b */`; `N'%राम%'` (Devanagari in a string); `ORDER BY ... OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY`; `UNION ALL` of two allowed tables. A string that holds words like `'please delete; drop table x'` is allowed and kept. `SELECT GrandTotal -- DROP TABLE Product\nFROM InvoiceInfo;;` is allowed and the statement that runs ends `FROM InvoiceInfo` (comment and `;;` gone).

Refused (query to reason): `DELETE FROM InvoiceInfo` to "Only SELECT"; `/* hi */ UPDATE ...` to "Only SELECT"; `EXEC xp_cmdshell 'dir'` to "Only SELECT"; `SELECT * FROM InvoiceInfo; DROP TABLE Product` and `SELECT 1; SELECT 2` to "one SQL statement"; `SELECT * INTO Backup FROM InvoiceInfo` to "INTO"; `WITH x AS (DELETE FROM InvoiceInfo) SELECT 1` to "DELETE"; `... WAITFOR DELAY '00:00:10'` to "WAITFOR"; `SELECT * FROM Registration` to "Registration"; `SELECT Password FROM Customer` to "Password"; `SELECT RTRIM(AccountNumber) FROM Customer` to "AccountNumber"; `sys.objects`, `sysobjects`, `dbo.sysdatabases` to "System"; `INFORMATION_SCHEMA.TABLES` to "INFORMATION_SCHEMA"; `OPENROWSET(...)` to "OPENROWSET"; `master..sysdatabases` to "sysdatabases"; `OtherDb..InvoiceInfo` to ".."; `OtherDb.dbo.InvoiceInfo` to "Three-part"; `FROM Estimate` and `FROM NotATable` to the table name; `SELECT @@VERSION` to "Variables"; `FROM #temp` to "temporary"; `FROM STRING_SPLIT('a,b', ',')` to "Functions"; `CROSS APPLY dbo.fn_x(c.ID)` to "fn_x"; an unterminated `'` or `/*` to "not closed"; `FROM archive.InvoiceInfo` to "dbo schema"; `WITH (TABLOCKX, HOLDLOCK)` to "TABLOCKX"; `Product p WITH (UPDLOCK)` to "UPDLOCK"; `SELECT NEXT VALUE FOR dbo.InvoiceSeq` to "NEXT VALUE FOR"; `SELECT Remarks FROM InvoiceInfo UNION SELECT Password FROM Registration` to "Password"; `... WHERE EXISTS (SELECT 1 FROM Activation)` to "Activation"; blank to "empty". `ExtraAllowedTables = [Estimate, Registration]`: `Estimate` becomes allowed, `Registration` never. Another test (`DataAndSettingsTests.cs` line 55) checks that **every one of the seven built-in reports passes the guard**; a third (`BusinessAssistantTests.cs` line 100) feeds `DROP TABLE Product` then `SELECT * FROM Registration` and expects the assistant to give up with the last refused query.

Derived by reading the code, **not run and not in the tests** (use as new vectors, and confirm by running): `SELECT * FROM Customer` is allowed and returns bank and tax columns (finding 2 in A3); `SELECT TOP 5 [Password] FROM Customer` is refused (quoted names are checked); `SELECT 1 FROM InvoiceInfo -- ; DROP TABLE x` is allowed and runs as `SELECT 1 FROM InvoiceInfo`; a cross join of three big tables without `TOP` is allowed (only the 5 s lock timeout, the 30 s command timeout and the 500-row cap limit it); a column alias named `Set`, `Use`, `Save`, `Go`, `Bulk` or `Into` is refused although harmless; a column or alias whose name starts with `sys` is refused; a column whose name merely contains `pass` or `token` (for example `Bypass`) is refused by the unanchored regex. These are false refusals that cost one retry, not holes.

**What `PiiMasker` does** (`Data/PiiMasker.cs`, 74 lines): applies to a `QueryResult` before the AI sees it (the screen shows the real values). A column is a "contact column" when its name matches `contact|mobile|phone|email|address|zipcode|pincode|gstin|aadha?ar|^pan$|accountnumber|ifsc` (case-insensitive). In such a column a string is replaced by `Partial` (keep first two and last two characters, put `min(6, length-4)` stars between; up to 4 characters all stars; empty or blank text left as is) and a non-string non-null value becomes `[hidden]`. In every other column, free text is searched with three regexes and each hit is replaced by `Partial`: an Indian mobile number (optional `+91`, then `[6-9]` and nine digits, single space or hyphen allowed between digits), a number dialled with a leading `0`, `+91` or `0091` (landlines with area code, mobiles with a 0), and an e-mail address. `MaskText(text)` does the same for chat text.

Masking vectors: from the test (`DataAndSettingsTests.cs` lines 70 to 83): columns `Name, ContactNo, EmailID, Remarks, GrandTotal` with `Sita`, `9876543210`, `sita@example.com`, `alt 91-9123456780`, `250` give `Sita`, `98******10`, an e-mail with no `example` in it, a remark with no `9123456780` in it, `250`; the original result is not changed. Derived by hand from the regexes (not run): `sita@example.com` becomes `si******om`; `alt 91-9123456780` becomes `alt 91******80`; `Call 98765 43210 now` becomes `Call 98******10 now`; `011-23456789` becomes `01******89`; `1234` (a value of 4 characters in a contact column) becomes `****`. **Not masked at all:** a name, a city, a state, `Remarks` without a number or an e-mail, a number that is not an Indian mobile or `0`/`+91` dialled number (a US `415-555-0100`, a UK number), a card number, an invoice number. So the masking is India-specific and name-blind (finding 1, 8 in A3). The dashboard has a second, broader number mask for screens (`Pos.Core/PersonalData.cs`: 7 or more digits with single spaces or hyphens become `98••••••10`; test `MoneyTests.cs` line 74) and Memory's `LongNumber` rule has the same 7-digit idea.

**What the Hub has today:** nothing like either (a search of `apps/business-hub` for SqlGuard, PiiMasker or contact masking found no file). `Ai/Routing.cs` only **detects** personal text (an e-mail, an international `+` phone number, a `ddd-ddd-dddd` phone, and a 13 to 19 digit run that passes the Luhn check as payment data) to pick a data class; it does not mask or remove anything.

**Porting notes (suggestions of this study, not from the old code):**
- The idea ports; the code does not. The Hub's database is SQLite with its own tables (`items`, `parties`, `documents`, `payments`, `stock_moves`, `audit_log`, the `ai_*` tables), so the allowed-table list, the denied lists and `BusinessNotes` must be rewritten for the Hub's schema, and the T-SQL words (`TOP`, `dbo`, `NOLOCK`, `sys*`, `GETDATE`) replaced by SQLite's (`PRAGMA`, `ATTACH`, `load_extension`, `sqlite_master`, `RECURSIVE`).
- Keep the layers: one statement, SELECT or WITH only, allowed tables, denied columns **including what `*` expands to**, row cap, timeout, always a read-only connection (SQLite: open read-only and `PRAGMA query_only`; the authorizer callback is the robust way to refuse everything that is not a read of an allowed column), mask before the AI sees it, show the SQL to the owner ("How this was found"), one retry with the reason as feedback.

The Hub's assistant must also obey the user's permissions (a cashier's assistant must not run a query over what a cashier cannot see): the old guard knows no user.

**The five photos.** The set is `PhotoKind`: 1 white background (pure white RGB 255, product about 85 % of the frame, soft studio light, no hands, no props; the main Amazon image), 2 in use (a real place from the AI's own description or `ShopProfile.TypicalPlace`; hands allowed, no faces), 3 to 5 one model each ("an emotional lifestyle photo of one model ... a genuine moment ... natural expression rather than a posed stock-photo smile", clothes modest, no logos). The enum names are `EuropeanModel`, `IndianModel`, `EastAsianModel` and file prefixes `european-model`, `indian-model`, `east-asian-model` are still fixed in code (`ProductPhotos.cs` lines 23 to 62, `FilePrefix`); the **titles and the looks of the three people come from the customer's profile** (`ShopProfile.Models`, up to 3, title at most 40 and looks at most 120 characters; with no profile "Model 1/2/3" and no look asked). The AI's description of the product (`ProductUnderstanding`: display name, what it is, description, type, suggested category, colours, material, size, keywords, local name in the profile's second language, use-case scene, model person, notes) is asked once with photo 1 and stored in `product.json`; photos 2 to 5 get photo 1 plus that description so the product stays the same. **Poster rules** (pure code, tested): customer price = selling price (GST added when shop prices exclude it, `PosterPricing.CustomerPrice`); `LowestOffer(price, cost, gst, maxOffer%)` = `ceil(max(cost*(1+gst), price*(1-min(maxOffer,90)/100)))`, equal to the price when there is no cost or no allowed offer; `OfferPrice` = `max(ceil(price*(1-percent/100)), lowest)`; `PercentOff` rounds down; offers are whole rupees. Candidate rules (`PosterPicker`, `PosterRules.Default`): slow after 30 days, new within 30 days, sales window 30 days, look back 120 days, at most 24 candidates, photos first; products without stock or price never appear; the AI sees only the candidates and may not exceed each max offer; the AI's words are cut (headline 28, local line 40, subline 60, festival 24 characters) and a word with a number or money sign is replaced by the kind's default words (`PosterWords.FromAi`, `PosterKind.DefaultWords`). Vectors from `PosterTests.cs`: `CustomerPrice(55, 5, true)=55`; `(100, 18, false)=118`; `(84.32, 18, false)=99.5`; `(0, 5, true)=0`; `LowestOffer(55, 40, 5, 30)=42` (cost with GST 42 beats 38.5); `OfferPrice(55, 42, 30)=42` and also for 90 (clamped); `LowestOffer(50, 48, 5, 30)=50` (no room); `LowestOffer(50, 60, 0, 30)=50` (cost above price); `OfferPrice(10, 5, 5)` is null (too small to change the price); `OfferPrice(55, 30, 0)` is null.

**Creatives** (`CreativeWords`, `PriceTags`): the owner's own words may hold no digit (any script) and no `₹ $ € £ ¥ %`, `Rs`, `INR`, `रु` (the app draws every price); the shop name may hold a digit but no money sign; headline at most 60, line 90, notes 400 characters; quotes become apostrophes and control characters spaces, so the owner's words cannot start a new line of the prompt (a deliberate prompt-injection guard); at most 4 products and 2 look references; formats square 1080, portrait 1080x1350, story 1080x1920, banner 1200x628, A4 2480x3508. Price tags are drawn by the app in the brand's first colour and can be dragged; the export needs the "I checked the words and the prices" tick.

## B. The dashboard (`apps/pos-dashboard-service`)

### B1. Screens and features of the dashboard

The list of screens is in A1 (almost every row there is a dashboard page). This section is about **how the dashboard is built**, because it decides what can be reused.

- **Shape.** A Blazor Server app on .NET 10 (`src/SmartRetail.Pos.Web`, `Program.cs` 330 lines), Kestrel on `http://127.0.0.1:5080` only, `AllowedHosts` = `localhost;127.0.0.1` (blocks other host names), no HTTPS (traffic stays on the PC), and **no sign-in at all** ("This version assumes one trusted shop PC", README, *Security and privacy*). No security headers are set by the app except a Content-Security-Policy on the Google Lens page (`Services/GoogleLens.cs` line 224). Shown inside the add-on's WebView2 window or any browser. Fonts (Inter, Noto Sans Devanagari, SIL OFL) and styles are bundled, so the figures need no internet.
- **Projects.** `SmartRetail.Pos.Core` (net10, pure rules with no I/O: billing, analytics, posters, checks, actions, review, owner payloads, labels; **this is the reusable heart**), `SmartRetail.Pos.Data` (repositories: SQL Server for the old POS, and an in-memory demo shop with two years of generated bills), `SmartRetail.Pos.Vision` (camera search, B2), `SmartRetail.Pos.Web` (screens, services, workers). It also builds `SmartRetail.AI.Core` from the add-on folder and the licence libraries from `licensing/clients/dotnet` (`SmartRetail.Pos.Web.csproj` lines 4 to 11).
- **Data modes** (`Pos:Mode`, `appsettings.json`): `Auto` (default: reuse the add-on's saved connection, else search the PC like the add-on does, else the demo shop; done once at start), `SqlServer` (connection string in the git-ignored `appsettings.Local.json` or the `Pos__ConnectionString` variable), `Demo`. Shop name comes from the POS `Company` row unless `Shop:Name` is set. Receipt and billing defaults are India GST words in `appsettings.json` (`Tax Invoice`, `Thank you! Please visit again.`, `GstMode: Intrastate`, `PricesIncludeTax: true`, `RoundToNearestRupee: true`).
- **Read-only.** Every repository query goes through the same read-only executor as A4 (ReadUncommitted, 5 s lock timeout, rolled back); every query is parameterised and wildcards escaped (README). **Billing is a demo preview only**: `Pages/Billing.razor` works on demo data and never writes to the POS (Roadmap item 1 in the README: "Save bills to the live database" was never done).
- **The seam for the Hub (important).** The screens do not read tables directly. They read interfaces in `Pos.Core/Abstractions/Repositories.cs`: `IProductRepository` (search, find by code or barcode, stock batches), `ICustomerRepository`, `IStockRepository` (low stock), `IInvoiceRepository` (save, recent, search bills, get one, sales for a day), `ISalesFactsRepository` (bill span, `GetFactsAsync(range)`, products, bill times, count of bills with products) and `IShopChecksRepository` (prices, sold lines, bill stubs). All of Sales, Today, Growth plan, Fix now, Actions, Monday review, posters and the owner payloads are computed from the plain records those return (`SalesFacts`, `ProductFacts`, `PriceFacts`, `SoldLine`, `BillStub`). **So the Hub can reuse `Pos.Core` unchanged by implementing these six interfaces over its SQLite tables** (both are .NET 10). The SQL Server implementations (`Pos.Data/SqlServer/*.cs`) read these POS tables: `InvoiceInfo`, `Invoice_Product`, `Invoice_Payment`, `SalesReturn`, `Product`, `SubCategory`, `Temp_Stock` (stock batches, the price the till charges), `Customer` and the POS `Logs` table for the time of each bill (a search of `SqlServerSalesFactsRepository.cs` and `PosLog.cs`; the other repository files were not read line by line).
- **Bill times.** The old POS stores only the date on a bill; the dashboard reads the exact time from the POS's own `Logs` (a line "added the new bill ... having invoice no. '...'") and marks a bill typed in on a later day as "entered later" (`Pos.Core/Abstractions/BillTimes.cs`; README *Bill times*; on a restored real database all 2,998 bills had their line, 11 were entered later). **The Hub keeps real timestamps, so none of this is needed there**; keep only the "entered later" idea if the Hub allows back-dated bills.
- **Background workers** (all `AddLicensedWorker<>`, stopped when the licence is not valid): Codex update (every 6 hours), camera-search learner, photo maker, creative maker, poster artwork, Monday-review judging (hourly), chat-history cleanup (twice a day), memory review (two quiet minutes after a chat), owner-view send (every minute and within 20 s of a new bill), owner questions (every 5 s), website offers (every 10 minutes).
- **Quirks.** The database is looked for only once at start; if SQL Server is not up yet the dashboard shows the demo shop until it is restarted (the add-on's shell works around it by waiting up to 3 minutes and re-starting the dashboard; `Desktop/AppHost.cs`). Several PCs: only the "main PC" (first connected to the owner's Supabase) sends and answers; photos, listings, memory and decisions stay per PC and are not synchronised (README, *Several PCs in the shop*). The README names the customer's website repository `smartave99/demo_shop` and "Demo Mart" (a customer name in documentation).
- **What the Hub has today instead:** its own sales, stock and parties pages, a "reports page" and an `audit_log` (`docs/MERGE-PLAN.md`). A search for Fix now checks, posters, a growth plan, an actions ledger, a Monday review, camera search or an owner live view in `apps/business-hub` was not made in detail by this study; `docs/MERGE-PLAN.md` says the Hub has "Reports: partly" and lists "Extras: online shop link, gallery, camera, image reader ... the website and the dashboard are separate programs". Treat all of these as **not in the Hub** until a check says otherwise (see D).

### B2. Camera product search (DINOv2, ONNX), barcodes and Google Lens

**What a person sees.** A camera button in the search box of the side panel, the Products page, the Barcodes page and the top bar of every page. Hold a product up, press Take photo, press Find it (the camera turns off at once). A product whose barcode is in the photo comes alone, marked "Exact match"; otherwise (only when finding by look is on) up to five look-alike products, most alike first, each with its photo, the codes the till scans, price, stock and a 0-to-1 match score. The first is called "Best match" only when it leads the next by 0.05. Nothing is chosen from a photo alone: each card has its own button (copy the code for the POS; Show on the Products page; Add to the sticker list). The photo looked for is never kept and never sent anywhere. Files: `Pos.Web/Services/CameraSearchService.cs` (946 lines; find at line 765), `CameraSearchWorker.cs`, `Shared/CameraFind.razor`, `CameraDialog.razor`, `CameraSearchSetting.razor`, `wwwroot/camera.js`; engine in `src/SmartRetail.Pos.Vision` (977 lines in 8 files); settings `AI.Core/Settings/CameraSearchSettings.cs`.

**How it works** (read from the code):
1. **Barcode first** (always on): `Vision/BarcodeScanner.cs` uses ZXing.Net (`TryHarder`, `TryInverted`, `AutoRotate`) for EAN-13, EAN-8, UPC-A, UPC-E, Code 128, Code 39 and ITF. Each code read is looked up the way the till does (`BarcodeScanner.Forms` tries variants such as a UPC as EAN-13, then `IProductRepository.FindByCodeAsync`): a product's code or barcode, or a stock batch's code. Codes the POS does not know are listed as "unknown codes".
2. **By look** (off until the owner turns it on in Settings): `Vision/ImageEmbedder.cs` runs a DINOv2 ONNX model with ONNX Runtime on **2 threads**, one picture at a time, about 0.1 s a photo. Pre-processing (`ImageMath.Preprocess`, lines 56 to 80) copies DINOv2's own image processor: shortest side to 256 px (Catmull-Rom/bicubic via SkiaSharp), centre crop 224 x 224, scale to 0..1, normalise with the ImageNet mean (0.485, 0.456, 0.406) and std (0.229, 0.224, 0.225), input name `pixel_values`; output is `pooler_output` or, if absent, the first token of `last_hidden_state`; the vector is normalised to unit length (384 numbers for small, 768 for base).
3. **Colour** (`ColourHistogram.cs`): a histogram of the middle of the picture, hue 8 x saturation 3 x value 3, plus 4 grey levels, square-rooted and normalised, because DINOv2 goes mostly by shape.
4. **Score** (`VisualIndex.cs` lines 14 to 20, 100 to 103): `0.7 x similarity(look) + 0.3 x similarity(colour)`; each product counts once, by its most alike photo; nothing under **0.35** is shown; top 5; "sure" means the first leads the second by at least **0.05** (or is the only one). The index is in memory and safe to read while it is filled.
5. **What it learns from**: only products that have photos in the add-on's own product-photo store (A5): the newest phone photos and the white-background photo (the model photos with people and places are left out on purpose, `CameraSearchService.cs` around lines 735 to 748). **Photos or images already in the old POS (`Gallery`, `InvImg`, product pictures) are not used.** Each photo is looked at once; the vectors are kept as `visual.json` in the product's folder (base64 32-bit floats plus the model id; vectors from another model are never read, `Vision/VisualStore.cs`), so they move with the data folder. A background worker learns one product at a time and never while the data folder is being moved.
6. **The model** (`Vision/ModelDownloader.cs`, `VisionModels`): two pinned models, DINOv2-small (Meta, Apache 2.0, onnx-community's ONNX copy at a fixed revision, 88,532,934 bytes) and DINOv2-base (347 MB, `346,627,111` bytes), downloaded from `huggingface.co` **only when the owner turns finding by look on**, with size and SHA-256 checked as it arrives and again at every start; a file that is not exactly the model is deleted; kept in `%LOCALAPPDATA%\NextGenOS\Smart Retail POS AI\models`, never in the data folder. A better model arrives only with an app update; the owner presses "Use this model"; the new model is downloaded and checked while the old one keeps working, then the photos are learned again in the background and the old model's file is deleted. A mirror can be configured with all four of address, id, size and SHA-256 (`CameraSearchOptions`). (The exact SHA-256 values and revisions are in `ModelDownloader.cs` lines 25 to 50; not copied here.)
7. **Google Lens** (separate, no AI of ours): the "Google Lens" button opens a small page of the dashboard that shrinks the product's newest phone photo to at most 1600 px, redraws it (this drops location and camera data), and posts it as a form to `lens.google.com/v3/upload` from the owner's browser; Google's results open in the same tab; fall back "Copy the photo" and "Open Google Images". The page serves only photos the app made for that product, is never cached and leaks no referrer (`Services/GoogleLens.cs`, `Shared/LensLink.razor`; `npm run test:lens`). What Google shows is Google's; the app never reads it or changes a price from it.

**Rules and quirks.** The match score is explicitly "how alike the photos are", "not the chance that this is the product" (README). Only the product list the POS has can be found (the old POS's `Product` and `Temp_Stock`). Finding by look needs at least one product with a photo in the store; otherwise it says what to do. The camera works only for the dashboard's own pages inside the app window (any other page is refused, README *Photos and voice notes*). `SkiaSharp` (MIT) and `Microsoft.ML.OnnxRuntime` (MIT) are the native dependencies; ONNX Runtime and Skia natives ship in the package (`Vision.csproj` lines 12 to 16). An AMD, Intel or NVIDIA GPU is not used (CPU only, 2 threads); the Hub's `Ai/Hardware.cs` would be the place to decide otherwise.

**Test vectors.** From the README and tests: score weights 0.7 and 0.3; floor 0.35; sure margin 0.05; a photo of a demo oil's barcode finds it with nothing downloaded; with finding by look off, a photo of the oil bottle finds nothing and says where to turn it on; the tiny stand-in ONNX models make `VisionTests` and `CameraSearchServiceTests` run with no download (`Vision/make_tiny_models.py`); the real model is checked only when `POS_TEST_DINOV2` is set.

**Privacy and the Hub's rules.** The only network use is the one-time model download after the owner's click; that matches "no model is downloaded without the owner's explicit permission" (`CLAUDE.md` section 15). No face recognition and no person identification is done: the model compares whole product pictures, but a photo that holds a person is processed the same way and is not kept. Data class of a looked-for photo: `PUBLIC`/`INTERNAL`, never leaves; the model download carries no shop data.

**What the Hub has today:** a browser still capture (barcode and product photo only, `docs/V2-ARCHITECTURE-ASSESSMENT.md` section 2, "Camera analytics: Browser stills only"); no ONNX Runtime, no DINOv2, no vector search (pgvector is in the storefront only). `Ai/Contracts.cs` has `VisionProvider` and an `EmbeddingProvider` as interfaces with no implementation but the OpenAI-compatible chat/embeddings one.

**Porting notes.** Keep: the whole `SmartRetail.Pos.Vision` project (net10, MIT/Apache dependencies) as the first local `EmbeddingProvider` for images, with a Hub model registry entry per DINOv2 model (the Hub's `Ai/Models.cs` already moves a model through candidate, testing, shadow, in use, retired and "never downloads automatically"; the pinned size and SHA-256 check from `ModelDownloader` is what that registry lacks: "Models are only a list: nothing downloads, installs or checks a file yet", `docs/V2-ARCHITECTURE-ASSESSMENT.md` section 6). Replace: the photo source (the Hub's item pictures instead of the add-on's store), the lookup (`IProductRepository` over SQLite), the data folder path, the Windows-only `%LOCALAPPDATA%` path (use the Hub's data folder, Linux too). Add: a feature flag (off by default), the `ai` licence module check, an audit entry when it is turned on and when a model is downloaded, a per-site model folder, and the ONNX Runtime native files to `prerequisites.json` (`CLAUDE.md` section 6; `scripts/audit-prerequisites.mjs`).

### B3. The owner's live view and the cloud (Supabase): what goes where, and what must become opt-in

**What it is.** The one place where the old programs send shop data to the internet. The owner makes his or her **own Supabase project** (free plan is enough), runs `cloud/supabase-owner-view.sql` once (1,036 lines, safe to run again), and sees the shop from a phone or computer: today's sales against last week by this time, every bill today with its time, hour by hour, the last 7 and 60 days, best sellers, low stock, the Fix now list, and the Monday review ("Last week" tab). The web side exists twice: the plain HTML page `owner-app/` (`index.html`, `owner.js` 647 lines, `owner.css`, `config.js` with two empty values for the project's URL and public key, Supabase's own JavaScript library vendored under `vendor/`, version 2.117.2, MIT, content-security-policy allows only its own files and the project's address) and the **Live shop** admin screens of the website in this repository (`apps/storefront-web-mobile/src/components/admin/live/`: `LiveShop`, `AskShop`, `FromTheShop`, `ShopProductCard`, `SignIn`, `ScreenTabs`, about 3,600 lines with tests; route `src/app/admin/live`; uses `@supabase/supabase-js` and the `NEXT_PUBLIC_SUPABASE_URL` and `..._PUBLISHABLE_KEY` variables). The shop-PC side is in the dashboard: `Pos.Core/Owner/*` (what is sent), `Pos.Web/Services/OwnerViewService.cs` (643 lines, with `OwnerViewWorker` and `OwnerQuestionWorker`), `OwnerViewClient.cs`, `OwnerAnswer.cs`, `WebsiteService.cs`, `WebsiteSender.cs`, `WebsiteOffer.cs`, and Settings (`Shared/OwnerViewSetting.razor`, `WebsiteSetting.razor`).

**How a PC is connected (the security design).** (1) The owner signs up on the page and creates the shop (only the first shop in a project can be created). (2) On the page "Connect a shop PC" makes a one-time code like `ABCD-EFGH`, valid 15 minutes, single use. (3) On the shop PC (Settings, Owner's live view) the owner types the project's URL, the project's **public** key and the code. (4) The PC receives its own long random key (32 bytes, hex) from `connect_shop_pc`; Supabase keeps **only a SHA-256 hash** of it; the PC keeps it protected by DPAPI (A3). (5) With that key the PC can only call the few "send" and "take" functions; it cannot read anything back. A secret or `service_role` key is refused by the PC and the page. (6) Disconnecting on the page or on the PC makes the key stop working at once. (7) Row-level security on every table (`shops`, `shop_members`, `shop_devices`, `pairing_codes`, `shop_live`, `shop_days`, `shop_questions`, `shop_reports`, `shop_products`, `shop_product_photos`, `site_categories`); the functions are `security definer` and check the key's hash and the shop. (8) Optional **two-step sign-in** (authenticator app): `sign_in_strong_enough()` makes every read and every owner function refuse a password-only session, enforced in the database. (9) Limits: 25 products waiting at once, 20 kinds of report, an answer at most 262,144 bytes (the PC keeps it to 240,000), a question of 1 to 1,000 characters, 30 questions an hour, questions older than 30 days removed, a question taken but unanswered is taken again after 10 minutes. Tested on Supabase's own database image in Docker (`cloud/test/run.sh`): owner, stranger, the PC's key, expired codes, too much data, weekly reports, two-step sign-in.

**What goes up, exactly** (`Pos.Core/Owner/OwnerLive.cs`, `OwnerReview.cs`; function names from `OwnerViewClient.cs` lines 70 to 182):

**Findings against the Hub's rules** (`CLAUDE.md` sections 15 and 16, decisions 4, 11, 12):
1. It is **opt-in in the sense that the owner must create a Supabase project and paste its address, key and a code**; nothing is sent before that. Good. But it is one switch for everything: figures, bill numbers and times, product names, low-stock names, the weekly report and the question answers all go once connected; only the website product offer has its own switch. Decision 12 allows an opt-in **summary of totals only** (sales, stock levels, takings; no customer records, payment details or staff data). So the per-bill list, product names and the answers go beyond decision 12 and each needs its own plain-words consent.
2. **The question path can upload personal data.** The owner's question is answered by the shop's AI exactly as at the shop (same guard, same masking); the table (up to 100 rows) goes to Supabase. Since names, cities and remarks are not masked (A3 finding 1) and `SELECT *` can return bank columns (finding 2), customer names and bank columns can reach the project, and the hosted AI that wrote the answer saw them too. The README sentence "Only figures leave the shop" has this one stated exception ("the shop's AI's answer to a question the owner asks").
3. The data is **FINANCIAL** (and sometimes **PERSONAL**) and goes to a third-party service in whichever region the owner chose (the README suggests "Mumbai" as an example; nothing is fixed in code). The Hub's routing would classify it `FINANCIAL`: allowed only for a provider the owner configured and allowed that class for.
4. There is **no audit of what was sent**, and no preview ("what will be sent") screen other than the README.
5. The same Supabase project also carries the app's **update folder** (`cloud/supabase-app-updates.sql`: a public bucket `app-updates`, files at most 40 MB, only one uploader user can write). That is a software-update channel, not shop data; the Hub's decision 7 plans its own signed update offer, so this part is dropped or replaced.
6. Customer identity in documentation and tests: the dashboard README names the customer's website repository and "Demo Mart" (`smartave99/demo_shop`), and a search finds "Demo Mart", "Avenue" or the customer's name in `owner-app/owner.js`, five browser tests (`owner*.e2e.js`, `live-shop.e2e.js`) and three unit-test files (`CreativeTests.cs`, `OwnerViewTests.cs`, `DemoStoreTests.cs`). Replace with neutral demo names when the code moves.

**Porting notes.** Keep the **ideas and the SQL security model** (pairing code, key hash, security-definer functions, row-level security, optional two-step, limits, the PC-can-only-send design, the per-product approval before anything is published) as the design of decision 12's head-office view, reuse `Owner/OwnerLive` and `OwnerReview` as the payload code after removing what decision 12 does not allow (or putting each part behind its own switch), and make the cloud project a replaceable "relay" provider (the owner has not said whether Supabase stays; see D). ## C. How each piece would plug into the Business Hub

### C1. The Hub's AI foundation (Phases 1 to 3) in a few paragraphs

Sources: `docs/V2-ARCHITECTURE-ASSESSMENT.md` sections 3 to 8 and the code in `apps/business-hub/src/NextGenOS.Hub.Core/Ai/` (2,209 lines in 12 files), read here only as far as needed. Nothing of it was run by this study.

**Phase 1, the AI foundation (built, tested by its authors, not run on real hardware or a real model).** Everything starts **off**. `FeatureFlags.cs`/`Vocabulary.cs` hold eight switches (`ai_assistant`, `camera_analytics`, `local_embeddings`, `remote_ai`, `business_ontology`, `event_engine`, `predictive_inventory`, `advanced_rules`); a switch counts only when the owner chose it **and** the signed licence has the module `ai` (`LicenceEntitlements.cs` line 13: `state.IsUsable && state.HasModule(module)`); each change is audited. Business code never calls a service itself: it asks `AiGateway` (`Gateway.cs`) with an `AiContext(Feature, DataClass, UserId, Flag, PreferredProvider)`. The gateway checks the licence and the flag, **raises the data class by looking at the text** (a card number makes it `PAYMENT_SENSITIVE`; an e-mail or phone makes public/internal/confidential text `PERSONAL`, `Strictest`), asks `Routing.Decide` which services may take that class (`PAYMENT_SENSITIVE` and biometrics never leave the computer; a service on this computer may take anything else; the shop network takes public and internal data and the rest only with the owner's permission; online services also need the `remote_ai` switch), checks budgets (requests a day, tokens a month, money a month; `Usage.cs`), tries the allowed services best first (`ProviderLocation.DefaultOrder`: local, local-optimized, lan, cli, api), records every use, refusal and failure, and returns an `AiAnswer<T>` that may be "no answer". A feature **must cope with no answer** (nothing in the shop depends on one). In front of the gateway `AiJobQueue` (`JobQueue.cs`) has three importances (a person waiting, normal, background), runs a few at once, lets a waiting or running request be cancelled, and turns the least important away when too many wait. Services are configured data (`Providers.cs`: connect, change, switch on, remove, per-service permission per data class and per feature, limits, a Test button); `Endpoints.cs` checks that a service called "on this computer" is really loopback, "in the shop" a private address, and an online one https (looked up at connect time, no redirects, no proxy); keys go to the Windows Credential Manager or an AES-256-GCM vault file (`Secrets.cs`; Windows store **not run**, no Windows here); `Hardware.cs` says which of six profiles the computer is (unknown stays "unknown"); `Models.cs` is a registry (candidate, testing, shadow, in use, retired, rolled back) that **downloads, installs and checks nothing**; the screen is Settings, AI helpers (owner only; `Web/Components/Pages/AiSettings.razor`). Tables `002_ai_foundation.sql` with `tenant_id` and `site_id` and a tested rollback; a copy of `shop.db` before any update (`VACUUM INTO`).

**The contracts** (`Contracts.cs`): `IAiProvider {Id, DisplayName, Location, Tasks, CheckAsync}` with typed children `ILlmProvider.GenerateAsync(LlmRequest messages)`, `IEmbeddingProvider.EmbedAsync(text inputs)`, `IVisionProvider.AnalyzeAsync(one image, one question)`, `ISpeechProvider`, `IOcrProvider`, `IRerankerProvider`, `IObjectDetectionProvider`, `ISegmentationProvider`, `ITrackingProvider`. **Implemented: one adapter, the OpenAI-compatible one** (chat and embeddings; covers Ollama, LM Studio, llama.cpp, vLLM, a LAN server, OpenRouter, OpenAI; tried only against a stand-in web server). **The gateway has methods for `Generate` and `Embed` only.** Not in the contracts, and needed by the old features: image **generation or editing** (there is no such `AiTask`: the tasks are generate, embed, vision, speech, ocr, rerank, detect, segment, track), several images in one request, audio next to text, a JSON schema for the answer, a thinking level, streaming of the answer, a model per job, a web-search capability, image embeddings (the interface says "text (later pictures)").

**Phase 2, events** (`Events/`; owner switch `event_engine`, plus the licence): observations (what a model or sensor saw, short-lived, never a business fact) kept apart from events (a business fact with who/what, where, when, how sure, why it is believed, what made it); append-only; wrong events rejected or superseded, never edited; provenance ("Why?"); evidence is a pointer, never the content; anonymous opaque references (`track:cam1:17`, `product:123`), names, e-mails, phone numbers and card details refused; retention and forgetting every ten minutes. Nothing in the shop writes events yet and there is no way in for other programs. **Phase 3, the business map** (`Ontology/`): seven kinds of thing read **in place** from the shop's own records (product, party, user, document, payment, table, project), four native kinds (site, zone, shelf, device), connections as data with begin and end dates, derived connections worked out when asked. **Phases 4 to 8** (business intelligence, embeddings and knowledge, the assistant, cameras, advanced) are not started. The assessment's decision 1 said the Windows POS and the AI add-on would become "source systems" that feed events by read-only adapters; decision 26 (merge) replaces that for the POS, but the idea that AI-derived conclusions are observations/events with provenance still holds for what the add-on's features produce.

### C3. Porting notes: keep, adopt by adapter, drop

These are suggestions of this study, in the order that wastes least. They follow `CLAUDE.md` section 17 (reuse and edit, do not rewrite) and decisions 25 to 28.

**Keep as code (pure rules and their tests), the most value for the least work**
1. `SmartRetail.Pos.Core` (net10, no I/O): billing and money rounding, sales analysis, today figures, Fix now checks, actions and product tests, Monday review, poster pricing and picking, listing rules (AI.Core), creative words, labels and Code 128, owner payloads.

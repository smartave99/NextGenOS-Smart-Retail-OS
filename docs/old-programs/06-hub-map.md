### 1.2 How the parts depend on each other

```
Hub.Web ──► Hub.Core ──► NextGenOS.Tax      (money and tax: pure code + country packs)
   │            └──────► NextGenOS.Devices   (printers, barcodes)
   └──────────────────► Licensing, Licensing.AspNetCore   (licence gate, brand, theme policy, licensed worker)
```

- **Core never refers to Web or to the licence libraries.** It learns about the licence only through a function the host gives it (`AiOptions(Entitlements: DelegateEntitlements)`, `HubHost.cs:55`). Web calls Core services directly (in-process).
- **Tax is the only place money arithmetic lives** (4). Core converts between its minor-unit `long`s and the engine's text amounts at the edge. Devices knows nothing about the Hub: Core's `ReceiptLayout` builds a neutral `ReceiptDoc`/`LabelDoc` and Devices encodes it for a printer language.
- **Packs are data**, read at start from embedded resources and cached for the life of the process (`PackCatalog`, `IndustryCatalog`: `static` dictionaries behind a lock). A new pack file needs a rebuild (`country-packs/tools/cli.mjs` and `industry-packs/tools/cli.mjs` validate and sync copies; the gate fails on a stale copy).
- Configuration: `Hub:DataFolder` (where `shop.db`, `keys/` and the AI vault live), `Hub:ProfileFolder` (the customer's `profile/`, default `profile` beside the program). `Kestrel` binds `127.0.0.1:5280` only, `AllowedHosts` is `localhost;127.0.0.1` (**a counter PC on the shop network cannot reach the Hub today**; this is the biggest platform gap, `docs/OPEN-WORK.md` 1a).

### 1.3 Name hiding (Obfuscar): what it renames, and the rules it puts on code

The shipped Hub is run through `scripts/protect-dotnet.mjs` (called by `apps/business-hub/installer/build.mjs:42` and `build-linux.mjs:47` with `--partial NextGenOS.Hub.dll`), which hides every `NextGenOS.*.dll` of the package: `NextGenOS.Hub.dll` (the web program), `NextGenOS.Hub.Core.dll`, `NextGenOS.Tax.dll`, `NextGenOS.Devices.dll`, `NextGenOS.Licensing.dll`, `NextGenOS.Licensing.AspNetCore.dll` (`installer/common.mjs:38`). The settings (`scripts/protect-dotnet.mjs:58-80`):

| Setting | Effect |
|---|---|
| `KeepPublicApi false`, `HidePrivateApi true` | public and private **types and methods are renamed** |
| `RenameFields true`, `RenameEvents true` | **fields and events are renamed** (including `public` fields and, probably, enum members: see below) |
| `RenameProperties false` | **property names are kept** in every assembly |
| `HideStrings true` | string literals are hidden (decoded at run time) |
| constructors (`.ctor`) | skipped: **constructor parameter names are kept** (JSON readers and the DI container match by them) |
| `--partial NextGenOS.Hub.dll` | for the web program **all methods and properties are kept** (`SkipMethod`, `SkipProperty` for every type); only its types and fields are renamed, because Blazor, the router and the policies find screens and handlers by name at run time |
| the map file and `.pdb` files | deleted from the package |

The rules this gives new code (the longer account: `docs/SECURITY-MODEL.md`, "Layer 3"):

1. **Web must not implement an interface that has methods, or override a virtual method, that one of our other assemblies defines** (Core, Tax, Devices, Licensing, Licensing.AspNetCore). Those methods are renamed in their assembly, the web program keeps its method names, and the loader stops with "inconsistent virtual method". The fix used: hand Core a **function** instead (`DelegateEntitlements(Func<string,bool>)`, `Core/Ai/FeatureFlags.cs:20-23`, built by `Web/Auth/LicenceEntitlements.cs`). An interface with **only properties** is safe, because properties are never renamed (that is why `ProfiledBrand : IBrandOverrides` works: `IBrandOverrides` has only `Current`). Inside Core, interfaces are fine (`IClock`, `ISecretStore`, `IProviderFactory`, `IHardwareProbe` are implemented inside Core and by test code), because every method of Core is renamed consistently.
2. **Only the full gate sees a breakage of rule 1**: `dotnet test` runs the unhidden build. The checks that run the hidden program are `hub-release`, `hub-protected-e2e` (every browser test again against the protected build) and `hub-installer`, and `audit-package.mjs` proves that the real type names of our source (172 names) no longer appear in the package.
3. **Do not persist or compare anything derived from a type, method or field name**: no `GetType().Name`, `typeof(X).FullName`, `Enum.ToString()`/`Enum.Parse` for an enum that is stored or sent, no `[Serializable]`/binary formatters, no reflection by name (`GetMethod`, `GetField`; none exists today in Core or Web, searched). Store **strings you choose** (document types `"invoice"`, status `"issued"`, roles, permissions, `FlagKey` strings, `EventType` strings): all of the Hub's persisted vocabulary is string constants (`DocTypes`, `DocStatus`, `Perm`, `Roles`, `FlagKey`).
4. **Serialise through properties, not fields.** `System.Text.Json` and Newtonsoft both work on properties (kept), constructor parameters (kept) and `[JsonPropertyName]`/`[JsonProperty]` attributes. A class that exposes data as a **public field** loses its name in the hidden build. Records with positional parameters are fine (their members are properties).
5. **Enums that are stored by name**: `PrinterLanguage` (`EscPos`, `Zpl`...) is saved by name in the `printers` setting through `JsonStringEnumConverter` (`Core/Printing/PrinterStore.cs:9`), and `NextGenOS.Devices.dll` is hidden. Whether Obfuscar renames enum members is **Not understood** from the code alone; the printer screens' browser test (`e2e/devices.e2e.mjs`) runs against the hidden build in `hub-protected-e2e`, which suggests it works, but no unit test pins it. For a new stored choice use a string constant or a numeric value, not an enum name.
6. **Resource names are explicit** (`LogicalName` in the csproj) so renaming types does not move them: `HubDb.Migrate` finds its steps by the prefix `NextGenOS.Hub.migrations.`, packs by `NextGenOS.Hub.industries.` and `NextGenOS.Tax.packs.`, the design tokens by `tokens.css`. A new embedded file must set its own `LogicalName`.
7. **What is only partly hidden** (so a reader of the shipped program can see them): all method and property names of `NextGenOS.Hub.dll` (screens, handlers, `HubHost`), all property names of every assembly (the shapes of `ShopSettings`, `Document`, `TaxResult` and so on), the JSON text keys the program reads or writes (camelCase), the table and column names in SQL strings (`HideStrings` hides the literals, but they are decoded at run time and the SQLite file itself is plain), and anything in the data files (packs, `profile/`, `tokens.css`, `wwwroot`). Name hiding is "days of work, not impossible" by its own account.
8. **The licence is what protects the product**, not the hiding (`docs/SECURITY-MODEL.md`). Code that must not run without a licence goes behind `UseLicenceGate` or `AddLicensedWorker`.

## 2. HubApp and its services

`HubApp` (`apps/business-hub/src/NextGenOS.Hub.Core/HubApp.cs`, 98 lines) is the one object that holds every service over one shop database. It is built once, as a **singleton** by `HubHost.AddHub` (`Web/HubHost.cs:55`: `HubApp.Open(Path.Combine(folder, "shop.db"), ai: ...)`), by the demo company builder, and by every test fixture (`HubApp.Open(path, clock, printService, aiOptions)`, `HubApp.cs:92`). `Open` creates the file if needed, runs `HubDb.Migrate()` (see section 3), then wires the services by hand in the constructor (`:25-52`). There is **no dependency-injection container for the domain**: to add a service you add a property and a line in this constructor (recipe 6.3). The Razor pages get `HubApp` injected and call the services directly in the same process (there is no REST API for the screens).

Every service is a class with a primary constructor taking `HubDb db`, `ShopContextProvider shop`, `IClock clock` and what else it needs. Services hold **no state of their own** except the shop-context cache, the AI job queue and the hardware-profile cache; everything else is read from SQLite on each call (each call opens its own short connection; `HubDb.Open` sets WAL, foreign keys on, busy timeout 5 s, `synchronous=NORMAL`).

### 2.1 Conventions every service follows

- **Refusals** are `HubException(code, plainMessage)` (`HubException.cs`). `Code` is a short stable word for tests and programs (`"duplicate-barcode"`, `"over-limit"`); the message is shown to the person as it is. A screen shows `ex.Message`; anything else becomes "Something went wrong, and nothing was saved" (`HubPage.Run`, `Web/Components/HubPage.cs:60`). **New refusals must be a `HubException` with plain words** or the screen shows the apology.
- **Writes that belong together** use `db.InTransaction((c, t) => ...)`; the inner overloads that take `(SqliteConnection c, SqliteTransaction t)` (for example `DocumentService.CreateDraft(c, t, ...)`, `Issue(c, t, ...)`, `Recalculate(c, t, id)`, `AuditService.Log(c, t, ...)`, `Numbering.Next(c, t, ...)`) exist so another service can join the caller's transaction. Use them to make one all-or-nothing action across services (this is how `Checkout`, `CreateProgressBill` and `SplitByLines` work).
- **SQL** is parameterised text with `$name` parameters passed as `("$name", value)` tuples (`HubDb.Exec/Scalar/Insert/Query`). Columns are read by name with `Reading` extensions (`r.Int("col")`, `r.Text`, `r.TextOrNull`, `r.Flag`, `r.Time`, `Data/Reading.cs`). No ORM.
- **Who did it**: methods that change something take `long? userId`. Pages pass `Me.Id`.
- **The audit log** (`AuditService.Log(userId, action, entity, entityId, detail)`; `Recent(limit)`) is written for: issue, void, credit-note, order-cancelled, user-created/on/off/role-changed/password-changed/login-locked, printer-saved/removed, bill-printed, drawer-opened, labels-printed, advance, fine, charge, fine-waived, copy-lost, and every AI switch and service change (`ai.*`). It is **not** written for: an item price change, stock adjustment (`CatalogService.Adjust` writes the `stock_moves` row with reason and user instead, not an audit row), a payment taken later (`AddPayment` writes the payment row only), party edits, settings saves done by `ShopContextProvider.Save` (check each Settings handler: Not understood whether all write an audit row).
- **Services do not check permissions.** Pages and endpoints do (`[Authorize(Policy = Perm.X)]`). Anything new that calls a service from outside a page (an endpoint, the assistant, a job) must check `Roles.Can(role, Perm.X)` itself (see 5.3).

### 3.1 Conventions (read before adding a column or a table)

- **Money**: whole minor units in `INTEGER` columns named `*_minor`. **Quantity**: thousandths in `*_milli`. **Percent**: thousandths of a percent in `*_pct_milli`. **Time**: UTC text `YYYY-MM-DDTHH:MM:SSZ` (`Iso.Text`), compared as text, so ISO ordering works in SQL. **Flags**: `INTEGER` 0 or 1 (`Reading.Flag`). **Free-form maps** (`attrs`, `meta`, `adjustments`, `result`): JSON in a `TEXT` column.
- **Ids** are `INTEGER PRIMARY KEY` (SQLite row ids). The shop tables of step 1 have **no `tenant_id` or `site_id`**; every table from step 2 on has `tenant_id TEXT NOT NULL DEFAULT 'local'` and `site_id TEXT NOT NULL DEFAULT 'main'` as the first two columns of the primary key (`CLAUDE.md` section 15). The code uses the constants `FeatureFlagService.Tenant = "local"` and `Site = "main"` (`Ai/FeatureFlags.cs:31`) and every query filters on them.
- **Nothing is deleted** from the shop's own records except drafts (`Discard`, `DiscardStaleDrafts`) and lines of an open document; people, items and tables are made inactive. Foreign keys are on (`PRAGMA foreign_keys=ON` in `HubDb.Open`).
- The database connection string has `Pooling = false`; each call opens and disposes its own connection.

### 3.4 How migrations and backups work

- `HubDb.Migrate()` (`Data/HubDb.cs:41`): creates `schema_version` if missing, reads the highest version, lists the embedded resources named `NextGenOS.Hub.migrations.NNN_name.sql` (the csproj embeds `Data\Migrations\*.sql` with that logical name, `NextGenOS.Hub.Core.csproj:22`), **sorts them by name (ordinal)** and runs each step whose number is higher, **each in its own transaction together with its `INSERT INTO schema_version`**. The number is the part of the file name before the first `_` (`VersionOf`). So files must be named with a **zero-padded number**, in order, with no gaps being skipped on purpose.
- It runs on **every program start** (`HubApp.Open`), so a new file in `Data/Migrations` is applied the first time the new program opens an old shop database.
- **Before the first step of an update to an existing database** (`current > 0` and at least one step is pending) it makes a whole copy next to the file with SQLite's `VACUUM INTO`: `shop.db.before-update-<from>-to-<to>.bak` (a timestamp is added if the name exists). A new database (version 0) is not copied. If the copy fails the problem is kept in `HubDb.BackupProblem` and **the update still runs** (Not understood whether any screen shows `BackupProblem`; searched: only tests use it).
- **Nothing in the running program offers a way back.** `HubDb.Rollback(toVersion)` exists for the person who looks after the computer and for tests: it checks that **every** newer step has a rollback file, makes the same kind of copy (`before-undo-<n>-to-<m>`), runs each rollback newest first in its own transaction and deletes the `schema_version` row. Version 1 can never be undone (`Rollback(0)` throws).
- **Rollbacks are pinned by tests**: `AiServicesTests.cs:441-490` (undo to 1 removes only the later tables, keeps sales and items, then forward again gives versions 1,2,3,4; every new table has `tenant_id` and `site_id`; the copy exists), `EventStoreTests.cs:513,528`, `OntologyTests.cs:400`, and `CoreTests.cs:20` (versions `1,2,3,4` once each).
- The upgrade path has **never run on a real old shop database**: only freshly made files and test files (`docs/OPEN-WORK.md`, "What cannot be verified").

### 3.5 How to add a table, with its way back (exact steps)

1. Create `apps/business-hub/src/NextGenOS.Hub.Core/Data/Migrations/005_<name>.sql` (next number). Only `CREATE TABLE` / `CREATE INDEX`; never alter or drop an existing table or column (`CLAUDE.md` section 15). Every new table: first columns `tenant_id TEXT NOT NULL DEFAULT 'local', site_id TEXT NOT NULL DEFAULT 'main'`, and include them in the primary key and in the first column of each index, as `003` and `004` do. Money `*_minor`, quantities `*_milli`, times UTC text.
2. Create `Data/Rollbacks/005_<name>.sql` that drops **only** what step 5 made, indexes first, newest table first, with `DROP ... IF EXISTS`.
3. Nothing to register: the csproj already embeds `Data\Migrations\*.sql` and `Data\Rollbacks\*.sql` (`NextGenOS.Hub.Core.csproj:22-24`).
4. Update the **tests that list versions**: `CoreTests.cs:20`, `AiServicesTests.cs:470` and `EventStoreTests.cs:505` (each has `new long[] { 1, 2, 3, 4 }`) expect exactly versions 1 to 4. Update the table lists in `AiServicesTests.cs:~445` (the `Except(...)` lists of "tables a shop sells with") and add a test like `Undoing_the_AI_step_removes_only_its_tables_...` for your step (undo to the step before, keep sales, run forward again, tables have `tenant_id` and `site_id`).
5. Because the gate checks rollbacks and migrations through those tests, run `dotnet test apps/business-hub/NextGenOS.Hub.slnx`.
6. If a **column on an existing table** is needed (for example a customer's opening balance or an item's HSN code), the rule says new tables only: put it in a new side table keyed by the existing id (for example `item_tax_info(item_id, hsn, ...)`), or, for loose facts, in the `attrs` JSON of the item or the `meta` JSON of the document. Changing `001` is not allowed; adding a column by a new migration is not forbidden by the rule's words ("never drop or rewrite a production column or table"), but every rollback of it is hard in SQLite (it cannot drop a column in older versions) and no step has done it yet: **ask the owner before the first `ALTER TABLE`**.

## 4. The money path

Everything about a sale is in one class: `DocumentService` (`apps/business-hub/src/NextGenOS.Hub.Core/Documents/DocumentService.cs`, 515 lines), with the arithmetic in `libs/dotnet/NextGenOS.Tax/TaxEngine.cs` (363 lines). **No other code in the Hub works out tax or a total** (reports only add up what these stored). Compare the old POS against the numbers in 4.7.

### 4.1 Units and conventions (the first things to get right)

- Money is a whole number of minor units (`long`, "paise"); the number of decimals is the country's (`currency.decimals`, 2 for India, 0 for Japan, 3 for a dinar) and is copied onto each document (`documents.currency_decimals`). Quantity is thousandths (`qty_milli`: 1000 = 1; 2.5 kg = 2500). A percent is thousandths of a percent in the database (`discount_pct_milli`: 10 % = 10000) and a decimal text in the engine (`"10"`). Times are UTC text `2026-10-05T06:30:00Z` (`Iso.Text`, `Clock.cs:29`).
- The engine works in `BigInteger` and takes and gives **text** amounts (`"199.50"`); `MoneyText.Parse(text, decimals)` refuses more decimals than the currency has (`MoneyText.cs:11`). The Hub converts at the edge: `MoneyText.Minor(minor, decimals)` to text going in, `MoneyText.Parse` coming out (`DocumentService.cs:231-235` and `:215`).
- The one rounding rule everywhere is **round half up on non-negative whole numbers**: `R(a, b) = floor((2a + b) / (2b))` (`TaxEngine.cs:17`). There is no banker's rounding and no floating point in the money path. (Two small places outside the engine round on their own, see 4.6.)
- All figures of a document are **stored on the document row** when it changes and are never recomputed afterwards (a final document's amounts never change). The engine's full answer is kept as JSON in `documents.result` (Newtonsoft, camelCase names from `[JsonProperty]`), and reports read it back.

### 4.2 What goes into a line, and what the Hub does NOT pass to the engine

A document line (`document_lines`, `LineInput` in `Documents/Models.cs:39`) has: item, description, `qty_milli`, unit, `unit_price_minor`, `discount_pct_milli`, `tax_code`, `customer_discount` (a country-pack discount code such as the Philippine senior discount), note, station, boq id. `DocumentService.Calculate` (`:224-240`) turns each line into a `TaxLineInput` with only: name, qty, unit price, tax code, **percent** discount, customer discount.

**Not passed, so not possible today in the Hub (a port of the old India POS must add them; the engine already supports them):**
- `CessPercent` (compensation cess) is never set. The engine and the pack handle it (vector "IN: old 28% rate with 12% cess"), the receipt and tax report already print a cess row, but no screen, column or service sets it. `documents.tax_minor` is computed as components + cess (`:216`), so it is ready.
- `DiscountAmount` (a fixed rupee discount on a line). Only percent discounts exist. A fixed discount on the whole bill does not exist either (adjustments are surcharge, fee, tip, advance, retention, never a discount).
- No HSN or SAC code on an item or a line (searched: nothing in Core or Web). The Hub carries a tax *code* (`GST0`, `GST5`, `GST18`, `GSTEX` ...), not a per-product HSN.
- No per-line tax-inclusive or exclusive switch: `prices_include_tax` is per document (default from the shop setting `PricesIncludeTax`, which the setup wizard fills from the country pack `pricesIncludeTaxDefault`, true for India).
- No MRP, no batch, no expiry, no cost layers: stock is only a ledger of quantity moves (`stock_moves`), and the cost price on the item is simply overwritten by the last purchase price (`PurchaseService.Receive`, `Purchasing/PurchaseService.cs:33-50`). The stock report values stock at that last cost (`ReportService.StockValues`, `(2 * onHand * cost + 1000) / 2000`).

### 4.3 The exact order of operations for a counter sale

`DocumentService.Checkout(CheckoutRequest)` (`:321`) runs **one SQLite transaction** (`HubDb.InTransaction`) that does 1 to 8 below and rolls everything back, including the document number, if anything throws.

1. **Draft**: `CreateDraft` (`:84`). Reads the shop context (`ShopContextProvider.Current`: settings plus country pack plus industry pack, rebuilt when settings are saved). Inserts `documents` with status `open`, `direction` `out`, and **copies these settings onto the document** so a later settings change cannot alter an old bill: `currency_decimals`, `prices_include_tax`, `seller_region` (shop's `Region`), `buyer_region` (customer's `Region`), `round_total`, `registered` (= `TaxRegistered`), and the adjustments JSON. Only `order`, `quote` and `purchase` get a number now; an `invoice` draft has none (number is null).
2. **Lines**: `AddLine` (`:117`) for each line. Checks in this order: item exists and is active; description given; quantity > 0; a quantity that is not a whole number is refused (`qty-whole`) for an item whose unit is `pc`, `plate`, `cup` or `glass` unless the shop has the `weighedItems` feature (`:125`; other units such as `kg` or `l` accept fractions in every industry; the `or` there is a pattern combinator, so the condition is as it reads); price = given price, else the item's price for the customer's price level (`Item.PriceFor`: `trade` customers get `trade_price_minor` when the item has one, otherwise `price_minor`); price not negative; discount percent between 0 and 100000 thousandths; tax code = `ShopContext.TaxCode(input ?? item.TaxCode ?? "standard")` (a class name `standard`/`reduced`/`zero`/`exempt` is turned into the country's rate code; a country without a `reduced` class falls back to `standard`, and `zero` and `exempt` fall back to each other); a customer discount code must exist in the country pack.
3. **Recalculate** (`:207`) after every change to lines, adjustments or party: reads header, lines, adjustments; calls the engine; writes `result` (JSON), `subtotal_minor` = engine `totals.taxable` (**the value before tax, not a sum including tax**), `tax_minor` = sum of the components plus cess, `total_minor` = `grandTotal` (after the round-off), `payable_minor` = `payable` (grand total + tips - advances - retention, never below 0), `tips_minor`, `retention_minor`, `advance_minor`.
4. **The engine, per line** (`TaxEngine.cs:36-104`, SPEC `country-packs/SPEC.md` section 5):
   - `gross = R(qty_milli * price_minor, 1000)`.
   - `discount = R(gross * discountMilli, 100000)` where `discountMilli` is the percent x 1000 (so a 10 % discount is `R(gross * 10000, 100000)`); clamped to `gross`; `net = gross - discount`.
   - Tax is zero when the seller is not registered, or the rate is `exempt` or `zero`, or the model is `none`. Otherwise `r` = the rate in milli-percent (for the `regional` model, the sum of the region's components).
   - **Prices include tax** (India's default): `taxable = R(net * 100000, 100000 + r + c)`, `taxTotal = net - taxable`. **Prices exclude tax**: `taxable = net`, `tax = R(taxable * r, 100000)`.
   - India (`gst-india`): same state (buyer region empty or equal to seller region) gives two parts. Inclusive: `CGST = R(tax, 2)` (half up), `SGST = tax - CGST` (so the **odd paisa goes to CGST**: 99.99 at 18 % has tax 15.25 and gives CGST 7.63, SGST 7.62; 1.00 at 5 % gives CGST 0.03, SGST 0.02). Exclusive: `CGST = SGST = R(taxable * r, 200000)`, each half rounded on its own, so CGST + SGST can differ by one paisa from rounding the whole tax once (taxable 0.30 at 18 %: whole tax 0.05, halves 0.03 + 0.03 = 0.06; 3 x 33.33 at 5 % gives 2.50 + 2.50 on 99.99). Different state: one part `IGST` = the whole tax.
   - Line total = taxable + tax parts + cess. For inclusive prices it equals `net` exactly.
5. **Totals and adjustments** (`:106-214`): sums per field; then each adjustment in order, always worked from the **lines only** (never compounding): `surcharge` and `fee` = percent of the line taxable (default base) or of the line subtotal (`base: "subTotal"`) or a fixed amount, taxed only when a tax code is given (and then **always as tax-exclusive**, with its own parts, added to totals and the by-code buckets); `tip` and `advance` are fixed amounts; `retention` is a percent (rounded half up) or a fixed amount. `subTotal` = lines + surcharges and fees with their tax.
6. **Total rounding** (cash rounding, only if the document's `round_total` flag is on **and** the pack rounds): `grand = R(subTotal, inc) * inc` where `inc` is the pack increment in minor units (India: `"1"`, i.e. nearest rupee; `defaultOn: false`). Half rounds up (100.50 becomes 101.00; 1050.47 becomes 1050.00, round-off -0.47). Then `payable = grand + tips - advances - retention`. A tip is added after the rounding and is never rounded. **The Hub always passes the document's own flag (a `bool`), so the pack's `defaultOn` is only used once, in the setup wizard, when it copies it into the shop setting** (`Setup.razor:298`).
7. **Issue**: `Issue(c, t, id, options)` (`:252`). Refuses a document that is not `open` ("That document is already final."), or one with no lines and no surcharge or fee ("There is nothing on this bill yet"). It **recalculates once more**, then, in this order:
   - Type: an `order` becomes an `invoice` (the order number is kept in `meta.orderNumber`).
   - **Number**: invoices and credit notes get their number now (`Numbering.Next`, `Documents/Numbering.cs:18`). A quote or purchase order keeps the number it got at the draft.
   - **Payments**: payments with amount > 0 are summed. If the sum is more than `payable`: the difference is change, which must be covered by cash payments (else "More was paid than the bill, and the extra is not in cash"); the change is taken off the **last cash payment first** (`ReduceCash`, `:474`), `meta.changeGiven` and `meta.tendered` are stored, and the payment rows hold only what was kept. So a payment row never exceeds the bill.
   - **If the sum is less than `payable`** (and direction `out`, not a quote): with `OnAccount` (progress bills) the due date is now + terms days (the client's, else the industry rule `paymentTermsDays`, else `creditDays`, else 30) with **no credit-limit check**; with `OnCredit` the shop must have the `credit` feature on, the customer must have a credit limit > 0, and `already owed + this unpaid part` must not exceed the limit (error codes `no-credit`, `over-limit`); due date = now + customer terms (else the rule `creditDays`, default 30); with neither it fails with code `short` ("The payments (...) do not cover the bill (...)"). Purchases (direction `in`) have no such check.
   - Update the document row: type, number, `status = issued`, `issued_at = now`, `due_at`, meta, user.
   - Insert one `payments` row per tendered payment (`kind = payment`, method must be one of the shop's payment methods: shop setting, else the industry default `cash, card, wallet, bank`; case-sensitive), then `documents.paid_minor = sum`.
   - **Stock**: for an `invoice` going out, `MoveStock(-1, "sale")`; for a `purchase`, `MoveStock(+1, "purchase")`.
   - One `audit_log` row (`issue`, document id, number).
8. Returns `Get(id)`: header, party, lines, adjustments, the engine result, payments.

**Stock movement** (`MoveStock`, `:486`): lines are grouped by item; items with `track_stock = 0` or no item are skipped; one `stock_moves` row per item (`qty_milli` negative for a sale, `reason` `sale`, `document_id`, user, time). If the shop has `AllowNegativeStock = false` and `on hand + qty < 0` it throws code `stock` ("Only 1 of Rice left.") and the **whole sale rolls back**. On hand is always `SUM(stock_moves.qty_milli)`; there is no stored stock figure to get out of step. Stock is never reserved by a draft, a quote or an order; it moves only at Issue.

### 4.4 After issue: pay later, void, return

- `AddPayment(documentId, payment, userId)` (`:367`): only on an `issued` document; amount > 0; not more than the balance (`payable - paid`, code `too-much`); inserts a `payment` row and raises `paid_minor`. `Document.PaymentState` is `unpaid`, `partial` or `paid` (`Models.cs:32`).
- `Void(id, reason, userId, refundMethod = "cash")` (`:382`): reason required; refused if already void or if an issued credit note exists for it (`has-credit-note`). For an issued document: stock goes back (`+` for a sale invoice, `-` for a purchase, reason `void`), and if anything was paid, **one negative `refund` payment** equal to `paid_minor` is inserted and `paid_minor` set to 0. The status becomes `void` and the reason is appended to the notes. Audit row `void`. (An open document can also be voided here; an open restaurant order is cancelled by `RestaurantService.CancelOrder`.)
- `CreateCreditNote(invoiceId, credits[(lineId, qtyMilli)], reason, refundMethod, userId, refundPaid = true)` (`:409`): only for an issued **invoice**; per line it refuses more than was sold minus what earlier credit notes already took (matched by description, price and discount; code `too-many`); builds a credit-note draft with the same price, discount, tax code and `prices_include_tax`, takes a `CN-` number, `refundable = min(note total, invoice paid)` (0 when `refundPaid` is false), writes the note as issued with `paid_minor = refundable`, inserts a negative `refund` payment, lowers the invoice's `paid_minor` by the same amount, puts the goods back in stock (`+`, reason `return`), audits. The note's `registered`, seller and buyer region are copied from the invoice **after** the amounts were calculated, with no second recalculation (`:441`): the note's money was worked out with the shop's **current** settings (region, registered flag and `round_total`), the invoice's flags are copied afterwards. For normal use these are the same; this is a place where a changed setting could make a credit note differ from its invoice by a rounding step. The code comment says "a credit note never rounds", but the draft copies the shop's current `RoundTotal` flag, so Not understood whether that comment is true. Tests do not pin it.
- **No credit-note offset against what a customer owes.** `Outstanding` (`:462`) sums `payable - paid` of issued `invoice` and `progress-bill` only; a credit note against a credit sale with nothing paid has `refundable = 0`, leaves the invoice's `paid_minor` unchanged, and so the customer still "owes" the full invoice. There is no customer ledger, no balance column and no receipt document (`Numbering` has an `RCT` prefix, but no code makes a receipt). A port of old-POS customer ledgers, advances and credit notes needs a new master (recipe 6.3).
- `Discard(id)` throws away an unfinished (open, unnumbered) invoice or quote; `DiscardStaleDrafts()` (called by the background worker, see 5.8) deletes open, unnumbered invoice/quote drafts older than one day that belong to no project.

### 4.5 Numbering

`Numbering.Next` (`Documents/Numbering.cs:18`) in the caller's transaction: key = (type, fiscal year); `year_key = context.YearKey(local date)` where the fiscal year starts on the country pack's `fiscalYearStart` (India 1 April: 5 October 2026 and 31 March 2027 are year `2026`; 1 April 2027 is `2027`). It reads `number_series.next_no` (default 1), writes `next_no + 1`, and returns `PREFIX-YEAR-000001` (six digits, zero padded; prefixes `INV QUO ORD CN PO PB RCT`; an unknown type uses its upper-cased name). Because it runs in the same transaction as the insert, a rolled-back document gives its number back (**no gaps, no repeats**). Counters are per type and year, never per shop or branch. The database also enforces `documents.number UNIQUE`.

### 4.6 Rounding places outside the engine (they are the other half of "the numbers")

- `ShopContext.RuleMinor` (rule money amounts such as a fine per day): `Math.Round(value * 10^decimals, 0, AwayFromZero)` (`Shop/ShopContext.cs:98`).
- `RestaurantService.TipFromPercent`: `Math.Round(subtotal * percent / 100m, 0, AwayFromZero)` of the **before-tax subtotal** (`Restaurant/RestaurantService.cs:212`).
- `RestaurantService.EqualParts(amount, people)`: `amount / people` each, the remainder spread as 1 minor unit to the **first** people (10000 over 3 gives 3334, 3333, 3333).
- `BoqItem.AmountMinor = (2*qty*rate + 1000) / 2000` (half up) and `ReportService.StockValues` use the same half-up formula on integers (`Projects/ProjectService.cs:17`).
- `ReportService.Summary` average = integer division `total / documents` (truncates).

- **A touch-counter look already exists as a combination of tokens and is pinned by a browser test**: `e2e/theme.e2e.mjs:33-65` builds a profile `{density: touch, nav: bottom, cart: bottom, fontScale: 1.1}` and asserts `data-density="touch"`, the menu along the bottom edge and the cart below the items on `/sell`; `:85-105` has the owner choose `compact` and `cart left` and checks the cart is left of the items. What does not exist is a **name** for such a bundle, a per-screen choice, and a list-style item view.

**Two facts that matter for the owner's wish (a vertical list look for a normal monitor, a wide counter look for a touch screen):**

1. **The layout choice is one per shop, not one per screen.** `theme.local` is a row in `shop.db`, so every PC that opens the Hub (and every counter that later connects to a main PC) sees the same density, menu and cart position. Only light/dark is per browser (`localStorage`). A look per machine therefore needs a **per-browser override** (see below), or a per-device record on the main PC.
2. **Item choice on `/sell` is only a grid of tiles today** (`.items` of `.item-btn`). There is no list rendering of items and no table-style cart variant; "vertical list" needs a new markup branch in `Sell.razor`.

**Where a "look" setting plugs in (a plan from the code, not existing code; the three places in order of least risk):**

- **A. A named preset made of existing tokens (no change to the licence format).** A "look" is a bundle of the tokens above, for example *list* = `density comfortable or compact, nav left, navLabels full, cart right` and *counter* = `density touch, nav bottom (or top), navLabels icons or full, cart left or right, fontScale 1.10 to 1.20`. Add the preset list as **data** (a small JSON in the profile or `industry-packs`, because the preset names are words a customer sees: `CLAUDE.md` section 8), a "Look of this screen" choice at the top of the Look tab (`Settings.razor:~120`, handler next to `SaveLayout` at `:568`), which fills the five selects. `ThemePolicy`, `ThemeSettings`, `LocalThemeStore.Save`'s whitelist and the test vectors do not change, because no new token is invented. This gives the whole shop one of the two looks.
- **B. Per screen (per browser) override.** Mirror the way `hub-theme` works: `hub.js` gets `setLook(name)` that writes `localStorage` key `hub-look`; `theme.js` (the file that runs before first paint, `wwwroot/theme.js:1-10`) reads it and sets `data-density`, `data-nav`, `data-nav-labels`, `data-cart`, `data-scale` on `<html>`, overriding what `App.razor:8` rendered. The CSS needs no change (it keys on the same attributes). Add a button next to the light/dark button in `MainLayout.razor:30` (and clear the attributes' flash by doing it in `theme.js`, not later). The limits: the server-rendered values and the browser value can disagree for one frame if the script runs after the attributes are set (it does not, it runs in `<head>` before CSS); the setting is lost with the browser's storage (fine: it is a convenience); the content security policy allows script files only, so keep it in `theme.js`/`hub.js`.
- **C. A new token (for example `look: "list" | "counter"` or `sell: "tiles" | "list"`).** This changes `ThemeSettings`, the policy, the JavaScript twin and `licensing/testvectors/theme-policy.json` and the licence spec section 5.3: **spec first, then vectors, then all implementations** (`CLAUDE.md` section 4). Avoid it unless a preset (A) cannot say it. The **list rendering** itself needs only the Hub: an attribute such as `data-sell="list"` on `<html>` (written in `App.razor:8` from `Themes.Current` or a Hub-only setting) plus CSS for `.items`, or a `@if` in `Sell.razor` around lines 33-41 that renders rows (`<table class="tbl">`) instead of `.item-btn` buttons; the cart panel markup (`Sell.razor:46-110`) is independent.
- The two looks also decide **what the other screens do**: `density` already affects every page's padding and button size; the "wide counter" needs `main#content { max-width: 1240px }` (`hub.css:34`) relaxed for `data-density="touch"` and a bigger `.pos` cart column (390 px, `hub.css:95`), and the **bottom menu** already exists for `nav="bottom"`.
- Tests to add: a `Web.Tests/ThemeTests.cs` case that the preset yields the expected tokens; an `e2e` case (copy `e2e/theme.e2e.mjs`) that choosing the look changes `<html>` attributes and survives a reload; if B is chosen, a script test that `theme.js` applies the override.

### 5.7 The background worker

`Web/Auth/HubWorker.cs` (24 lines): a `BackgroundService` that calls `HubApp.Upkeep()` immediately and then every **10 minutes** (`PeriodicTimer`), logging a warning if it throws and carrying on. It is registered only as `AddLicensedWorker<HubWorker>()`, so it starts when the licence becomes usable and is stopped when it is lost (`LicensedWorker<T>` looks every 5 seconds and **creates a new instance** each time). `AddNextGenOSLicence` adds the licence library's own check-in worker (`LicenceWorker`) separately. See 6.6 for adding another job.

### 7.3 The fixtures you will use to port a rule

`HubFixture` (`tests/NextGenOS.Hub.Tests/HubFixture.cs`, 31 lines): `new HubFixture(country = "IN", industry = "retail", configure: s => ..., now: ..., printer: ..., ai: ...)` makes a temporary SQLite file, opens `HubApp` on it with a **`FixedClock` set to 2026-10-05 06:30 UTC (12:00 noon in India)**, saves a `ShopSettings { Name = "Test Shop", Country, Industry, SetupDone = true }` (with `Region = "27"` for India), lets `configure` change settings (for example `s => s.AllowNegativeStock = false`, `s.PricesIncludeTax = false`, `s.RoundTotal = true`), and deletes the files on `Dispose`. Use `f.Clock.Set(...)`/`Advance(...)` to move time, `f.App.<Service>` for everything. The pattern of a money test (from `CoreTests.cs:39-63`):

```csharp
using var f = new HubFixture("IN", "retail");
var rice = f.App.Catalog.Create(new ItemInput { Kind = "stock", Name = "Rice", PriceMinor = f.App.Shop.Current.Minor("118.00"), TaxClass = "standard" });
var view = f.App.Documents.Checkout(new CheckoutRequest { Lines = { new LineInput { ItemId = rice.Id, QtyMilli = 2000 } }, Payments = { new PaymentInput { Method = "cash", AmountMinor = 30_000 } } });
Assert.Equal(23_600, view.Document.TotalMinor);   // 2 x 118.00 with 18% included
```

A **worked example from the old program becomes a test like this one**: same items, prices, rates, quantity and payments, and `Assert.Equal` on `TotalMinor`, `TaxMinor`, `SubtotalMinor`, each `view.Result.Totals.Components[i].Amount` text, `PaidMinor`, `meta["changeGiven"]` and stock (`f.App.Catalog.OnHandMilli`). Build tax cases the same way for several rates and for the inter-state case by giving the customer a `Region` different from the shop's (`CoreTests.cs:80-88`). If a rule needs a new engine input, add it to the **vectors** first (4, 6.4).

Other helpers: `DemoCompany.Fill(path, new DemoOptions { Industry, Country })` makes two weeks of trading through the services (used by `DemoCompanyTests`, and by the set-up wizard's sample); `AiTestKit.FakeService`, `Entitled`; `Web.Tests/HubWebFactory`; the E2E host's switches `--E2E:Licensed=false`, `--E2E:White=none|theme|full`, `--E2E:Modules=hub,ai`, `--E2E:Brand=Name`, `--E2E:Seed=true`.

### 7.6 Costs (observed on this machine on 7 October 2026, by listing folders only; no command was run)

- This machine has **4 cores and 16 GB of memory**. The NuGet cache here (`~/.nuget/packages`) was **3.0 GB**, shared with the repository's other .NET programs; the biggest entries are SkiaSharp's native files for Windows (404 MB) and Linux (215 MB), the self-contained .NET runtime packs for publishing (253 MB Linux, 256 MB Windows) and the dashboard's ONNX runtime (385 MB, not used by the Hub).
- **Each build folder is large because SkiaSharp's native files and their `.pdb` files (90 to 97 MB each, for win-x86, win-x64, win-arm64 and others) are copied into every test project's output**: `apps/business-hub/tests/NextGenOS.Hub.Tests/bin` is 1.1 GB (527 MB for Debug and 527 MB for Release), `Hub.Web.Tests/bin` 1.1 GB, `NextGenOS.Hub.E2EHost/bin` 524 MB, `Hub.Web/bin` 1.4 GB, `NextGenOS.Devices.Tests/bin` 492 MB. A full gate plus a day of development can therefore hold **several GB** of build output. Deleting `bin` and `obj` folders is safe (they are rebuilt).
- `e2e/node_modules` is 13 MB; Playwright's Chromium (about 150 MB or more, downloaded by `npx playwright install chromium`) was **not installed here** (`~/.cache/ms-playwright` absent), so `hub-e2e` would SKIP on this machine.
- Each domain test makes its own SQLite file in the system temp folder and deletes it; each browser scenario starts its own Kestrel process on a free port and a fresh data folder, one scenario after another (so the 14 scenarios are slow compared with unit tests; **time was not measured**). `protected.mjs` publishes the E2E host again and runs Obfuscar before it starts. The `hub-release`, `hub-installer` and `hub-linux-package` checks publish the self-contained program (a few hundred MB each, **not measured**).
- xUnit runs test classes in parallel; tests that share nothing (each has its own database file) are safe to run together.
